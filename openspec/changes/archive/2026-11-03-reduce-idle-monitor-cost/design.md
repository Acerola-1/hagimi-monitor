# Design

## Context

见 `proposal.md`。只读审计已区分「代码上会跑」和「还没量过占多少」。本 change 的行为合同在 `specs/idle-probe-gating/spec.md` 与 `specs/menu-bar/spec.md`。实施顺序是先把下面的实测表填上，再改探针；低风险清理不依赖实测结果。

公网 IP 是网络明细的默认指标（`metric.network.public-ip`），不是没用的功能。统计库被设置页和报表读取。两者都不删除。

## Goals / Non-Goals

**Goals:**

- 用同一台机器、同一次构建，比较「面板关着」和「面板开着并展开 CPU/内存」的主线程与探针成本。
- 把结论写回本文件的实测记录，再决定条件项做不做。
- 低风险清理可以和实测并行，但不改变读数、文案和历史数据。

**Non-Goals:**

- 不重写 `MonitorStore` 的观察框架，也不把采样器改成 actor。
- 不缩短或清空统计保留。风扇 2 秒常驻告警不改。
- 不在实测完成前改 1 秒 CPU 占用采样、公网 IP 门控、蓝牙画像门控或温度键门控。
- 不把钉住面板高度或设置窗口分隔线当成这次的清理项；那两项要先目测，单独立项。

## Decisions

1. **实测先于门控。** 规格描述最终行为，但 `tasks.md` 里门控任务必须等实测记录标成「已填写」。这样计划可以反复改，而不会在还不知道大头是谁时先改周期。
   - 备选：按审计直接改。放弃原因：审计自己把 CPU 占比标成待验证。

2. **公网 IP 只停隐藏期的请求，不删指标。** 面板可见且指标开启时仍按现有 30 秒缓存查询，失败仍显示缺失或上次成功值。
   - 备选：删除指标和设置项。放弃原因：展开区默认就有这一格，删掉是功能回退。

3. **温度键看菜单栏选择，不看「直连版一律每秒读」。** 菜单栏含 CPU 温度时隐藏期照读。不含时，只在有面板可见时读。CPU 占用采样不动。两个 `SMCReader` 先不合并；合并连接不改变读数次数的大头，留到实测证明锁竞争后再说。
   - 备选：温度一律改成 2 秒。放弃原因：菜单栏正在显示温度时会改变现有节奏，规格不允许。

4. **蓝牙只停周期性系统画像。** 连断事件可以留下，打开面板时补一次画像。`refreshIO()` 若实测显示主线程可观，再把它移出主线程；那是条件项，不在第一批门控里。

5. **低风险清理的验收是「行为不变 + 警告减少」。** 火花线改用 `MonitorConstants.sparklineMaxPoints`（当前仍是 24）。`allFans()` 使用已缓存的风扇数，满足既有风扇规格，不新增规格。HUD 徽章按 `menu-bar` 增量规格订阅显隐。

6. **条件项单独开关。** 只有实测记录把「可见面板的视图 body」写成主要成本时，才增加拆分观察对象的任务。在那之前 tasks 里保持未启用。

## Risks / Trade-offs

- [打开面板的瞬间公网 IP 或蓝牙电量是旧值] → 可见时立即补一次查询；失败沿用现有缺失占位。
- [菜单栏温度开关和采样门控不一致，导致温度卡住] → 门控条件同时看「指标是否选中」和「是否有面板可见」，并加一个切换设置后的测试。
- [低风险清理里的字符串解码改法读坏 C 字符串] → 只替换编译器点名的 `init(cString:)`，空串仍当缺失；不改采样公式。
- [实测用 Debug 构建，绝对毫秒不能当发布结论] → 记录里只比较同一构建的前后占比，需要对外数字时再复测 Release。

## Migration Plan

1. 填写下方实测记录。没有记录就不动门控。
2. 低风险清理可以穿插进行，每项独立可回退。
3. 门控按规格落地后，用同一套追踪再填「改后」列。若空闲成本没有下降，回退对应门控，保留低风险清理。
4. 不迁移数据库，不改用户已有统计文件。

## Open Questions

后台那 100 多兆的构成仍然不知道。Allocations 的对象表没有从命令行导出，关面板之后的代际也没有做成。在点名常驻区域之前，不写「已经知道怎么降内存」。

条件项判定：

- 若「面板关闭」里温度键、系统画像或公网 IP 占了明显时间：按规格做门控。
- 若三者在 Time Profiler 里都接近噪声：门控仍可做（请求本身不该在没人看时发生），但不要据此再改 1 秒 CPU 占用。
- 若「面板打开」里视图 body 是主线程大头，且进程列表内容没变：在 tasks 里启用观察拆分。否则不启用。
- 2026-11-03 打开面板的 45 秒里没有采到视图 body。观察拆分不启用。关面板后的代际还没做成。

## 结论

2026-11-03，Direct Debug，没有改采样代码。

内存：面板关着时 RSS 大约在 103MB 到 175MB 之间，10 分钟没有单向上涨。没有对象清单，也没有关闭前后的代际，所以不知道这 100 多兆是缓存、映射还是常驻对象。本 change 没有解决后台内存占用。

CPU：温度键、蓝牙画像、公网 IP 都不是大头，门控仍可做，但不据此改 1 秒 CPU 占用。周期主要在电池采样、进程能耗、统计分钟汇总、Game HUD 前台识别。菜单栏当前没有电池这项，面板全关时电池仍在采样。观察拆分不启用。

这些 CPU 门控都不能当成把 100 多兆降下来的办法。若继续查内存，下一步是堆或虚拟内存快照，点名常驻区域。

## 实施笔记

2026-11-03 落地了第 2 组和第 3 组。第 5 组没做，后台那 100 多兆仍然没有降法。

改后的 Direct Debug 在面板关闭时跑了约 35 秒：进程没有 TCP 连接，也没有 `system_profiler` 子进程。这台机器的蓝牙行是关的，菜单栏含 CPU 温度，所以这次没有覆盖「蓝牙行开着」和「菜单栏不含温度」两种隐藏期。打开面板后补查公网 IP，没有再看。

Direct 测试整包跑过三次。有两次在整包并行时超时或缓存身份断言失败（面板快照、进程预取、菜单栏环图缓存），同一条单独再跑都通过。App Store Debug 构建通过。没有手点菜单栏、展开动画、报表页或游戏徽章。

## 验收返工（2026-11-03）

第一次实现的验收没有通过：温度门控漏了运行中的 Game HUD；指标文字模式没有绘制 HUD 徽章且去重键不含 HUD；停读后的旧温度仍被统计累计；公网 IP 与蓝牙画像在旧请求在飞时重开，会把立即补查吞掉；首次采样早于初始门控；另有三条既有业务编译警告。

返工后的行为：

- 温度消费者统一为「主面板可见、菜单栏选中温度、Game HUD 显示且勾选温度」三者的并集；初始门控在第一次采样前安装。
- 门控关闭只保留旧温度字符串作占位，`numericValue` 置空，不再作为新观测进入统计。
- 公网 IP 使用启用代次；旧回调既不继续备用源，也不能清新一轮的在飞标记。蓝牙画像在旧画像在飞时只排队一次补查，并在旧回调结束后立即续跑。
- 环形与指标文字模式共用徽章优先级：告警优先，其次 HUD；HUD 状态进入指标模式重绘键。
- 设置工具栏、钉住面板未用局部值、HardwareSysctl 泛型指针三条警告一并清理。

验证记录：

- 新增 15 条确定性测试通过，覆盖温度消费者矩阵、缓存温度不进入统计、公网代次、蓝牙待补查、徽章优先级与重绘键。
- Direct 全量测试 915 条通过；两条已知并行时序用例失败（面板快照、进程预取），单独复跑均通过。
- 用临时声明为游戏类别的应用触发真实 HUD：主面板关闭、菜单栏只显示 CPU 占用时，HUD CPU 温度两次截图从 93°C 更新到 95°C；指标模式菜单栏出现紫色 HUD 徽章，关闭游戏后徽章消失。
- 蓝牙行开启且面板关闭时未观察到 `system_profiler`/`pmset` 子进程；公网 IP 的交错行为由状态机单测覆盖，未做包级抓包。
- App Store 与 Direct 干净 Debug 构建均通过，业务 Swift 警告为 0；沙盒版原生面板两轮开关正常。

仍未完成：1.2 的面板关闭前后 Allocations Generation，以及 5.1 的常驻内存区域点名。`design.md` 与 `tasks.md` 保留这两项未勾选；本次没有把 CPU 门控说成内存修复。

## 归档后复审补修

归档后的异步专项复审又发现三处遗漏，已补修并保留在本归档记录中：

1. `ProfilerProbeState.setEnabled` 曾预占 `isInFlight`，生产入口随后再次 `request()` 会把自己判成“已在飞”，导致 `system_profiler` 永远不启动。现在启动权只由 `request()` 取得，定时器重叠不额外排队；实际打开蓝牙面板后观察到真实 `system_profiler SPBluetoothDataType` 进程。
2. Game HUD 首帧曾把门控关闭期间保留的缓存温度作为实时值；现在 HUD 只接受 `numericValue != nil` 的温度，缓存值显示缺失。
3. 环形菜单栏模式不渲染温度，但门控仍按“指标列表选中温度”放行；现在只有指标文字模式才把菜单栏温度计入消费者，并订阅显示模式变化立即重算。

补修后新增生产调用序列、HUD 缓存温度和环形模式门控测试。1.2、5.1 仍未完成。
