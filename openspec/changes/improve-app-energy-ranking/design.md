# 调查与落地决策路线

> 暂缓：这里只保存恢复后的调查方法与准入条件，不是已获验证的产品实现设计。用户重新启动工作后，先通过数据源决策关卡，再补齐最终实现设计。

## Context

动机与目标见 proposal.md，行为目标见 specs/app-energy-ranking/spec.md。已有报告记录 115 个 M4 / macOS 27.3 样本；独立 GPU 应用的组 GPU 时间约 638.2 ms/s、整颗 GPU 功率约 5.746 W，而组评分约 16.61。CPU 应用组评分约 637.78。该现象不能由第一轮混组单独解释，但不能外推为所有系统完全忽略 GPU。

现有实现以进程 CPU 纳焦耳计数差分计算 W，并按应用归属合并和 EMA 平滑。公式本身有依据，但 CPU 覆盖限制、退出残留、PID 复用平滑污染、短命进程遗漏等需要后续处理；这是代码审查发现，不等同于所有问题都已通过独立复现实验确认。

## Goals / Non-Goals

**Goals:**
- 保留可复算证据和用户需求，在恢复时避免从头调查。
- 以受控负载、同机系统界面对照和实际采样成本，决定数据源是否满足综合应用能耗排行。

**Non-Goals:**
- 暂缓期间不继续采样、不修改产品、不安装管理员助手、不替换当前排行。
- 不预先指定 powermetrics、GPU 时间分摊或其他估算模型为最终实现。
- 不把本次暂缓扩展到其他产品工作。

## Decisions

### 保存为暂缓 change，而不是归档为已完成

OpenSpec 保留需求、规格草案、决策关卡和后续任务；报告保留实测结论；本机档案保留含进程信息的原始数据。工具显示规划文件齐备，不表示调查通过或获准实施。相比仅留聊天或 tmp，这样便于后续查找且不混淆完成状态。

### 将数据源验证作为实施前置关卡

恢复后的首要工作是核对同一独立 GPU 负载在 powermetrics 评分、GPU 组时间、GPU 域功率和活动监视器中的表现，排查指标含义、平台支持与版本差异。网络、磁盘、媒体引擎和 ANE 覆盖不能由 CPU/GPU 测试代替。若候选评分不能解释覆盖，则选择明确受限的展示或继续寻找来源，而不是把评分包装为全应用瓦数。

### 明确保留三类候选

- 系统综合相对评分：验证覆盖、刻度、权限及开销后再决定是否采用。
- CPU 功率与 GPU 活动分项展示：可作为诚实回退，但不能单独满足完整应用耗电排行的目标。
- 自建估算模型：只有误差、覆盖与文案可接受时才讨论，不能按 GPU 时间机械分摊总瓦数后称为官方实测。

最终选择是恢复后需要完成的决策任务，不是当前被假定解决的开放问题。管理员助手及分发架构须在该关卡之后另行设计；已有 power-telemetry 对分项采样的无提权约束不被本草案改变。

## Risks / Trade-offs

- GPU 评分覆盖不足 → 先完成独立负载和系统界面对照，不凭手册描述直接上线。
- 采样自身耗电 → 本次两秒配置约占一个核心 2.7%，后续比较仅 tasks、较低频率及隐藏期策略；不把整个组合的开销归因给单一选项。
- 机型/系统差异 → M4 结果保留边界；未来按实际发布范围补证据，不冒充 M3 或全机型验收。
- 原始证据被临时清理 → 迁出 tmp，校验压缩原始数据并保存文件清单及独立压缩包。
- 进程归属导致误排行 → 校验应用身份、辅助进程及生命周期，再评估短命进程与共享服务边界。

## Migration Plan

当前没有部署或迁移。恢复后按 tasks.md 的调查关卡先完成数据源决策，再修订设计与验收范围；只有新的明确实施指令才进入产品改动。
