## 设置页应该如何改

页面首先回答三件事：当前是否真的承压、哪个应用值得关注、下一步去哪里查看。当前卡片把应用名、红色状态、平均值、峰值、开始时间、持续时间、三段彩条和三个档位时长同时铺开，且放进多层浅灰卡片中；小字与浅色文字多，视觉注意力被分散。

建议结构：记录控制 → 范围与监测摘要 → 应用占用摘要 → 核心用量/传输 → 完整报表入口。实时应用占用独立标“当前”，不让用户以为它跟随历史范围切换。

默认每个应用一行，图标 + 名称 + 主要占用 + 简短状态，最多展示少量应用。优先排序依据已证实的系统压力和占用程度，而不只是持续时间。更多应用通过“查看全部”进入报表。

示意文案（设计示意，时长需修复后重新计算）：

> 系统压力较低 · 有 2 个应用资源占用较高  
> Safari　内存平均 5.8 GB　[查看占用详情]  
> WindowServer　GPU 平均 46%　[查看占用详情]

每行展开后才显示峰值、起止、有效高占用时长。档位分布放事件详情，需要解释它是时长分布而不是时间线；零时长档位不必在摘要里展开。颜色不能单独承载判定，正常的高占用用中性/提醒色；有真实内存或热压力时才增强警示。

高占用本身不应直接写“正在产生持续系统压力”。内存固定 3.5 GiB 门槛没有考虑整机容量，CPU >=80% 被叫“满载”也缺少百分比基准解释。资源占用、系统压力与因果归因应是三个不同概念；时间重叠只能作为相关线索。

## 完整报表应该如何改

1. “查看明细”应直接打开对应应用/指标/事件。当前只跳到应用排行；事件行仅有名称、次数、最长时长、日期，无法查看原卡片中的指标与峰值，摘要到详情的链路反而丢信息。
2. 总览保留数据完整度、趋势和模块入口，但先给出一句可读结论。实机同时看到“100 分、压力较低”和“应用 2”；应明确评分反映什么，避免把它读成电脑全面健康诊断。
3. 综合趋势默认减少同时出现的曲线，允许按指标切换；资源利用率和内存压力放在同一百分比轴时必须明确含义，不能暗示可直接比较。
4. 应用排行改为可比较的列：应用、样本均值、峰值、有效高占用时间、估算累计消耗；提供查看全部和排序。当前仅展示前 8 项，副标题重复应用名，右侧核·时与中部百分比相距较远。
5. 历史快照写清更新时间；当前读数单独标注。应用排行当前写“实时统计”，但报表快照需要重新载入，容易造成预期偏差。
6. 时间范围名、单位、指标阈值、状态文案与设置共用定义；空数据、采样不足、中断、已恢复使用统一语义。

## 采集与架构判断

本次检查的是本地应用的采集、落库、聚合与展示链路，不是一个独立远端后端。现有分层有可保留的基础：系统指标采用分钟/小时/日汇总，真实秒数覆盖与休眠中断有明确处理；数据库和应用库各有串行队列；报表在后台读取、聚合；硬件探针共享 5 分钟缓存；关窗会取消任务和停止实时源。

首要改进是把应用告警也接入同样严格的时间/观测契约，避免系统级统计精细、应用级却按次数估算。增加一个纯计算事件状态机，以有效观测/未知/退出/休眠驱动状态；统一阈值配置，UI 不再复制档位数值。

性能候选：报表加载先显示统计结果，硬件资料随后补充。当前初始化仍等待硬件采集完成后才发布全部报表，尽管已有缓存，冷启动或慢设备仍可能拖延首屏。此项由调用链判断，未测量耗时，不能据此声称现有报表卡顿或改动后必然更快。应分别测打开到首个可读结果、范围切换、模块切换、长列表滚动以及隐藏后的开销。

## 独立验证结果

- t=0 和 t=60 秒的两个 CPU 高占用样本：显示 2 分钟，而两次观测间隔是 1 分钟。
