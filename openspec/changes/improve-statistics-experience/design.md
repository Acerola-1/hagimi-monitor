# Design

## Context

动机与授权范围见 [proposal.md](proposal.md)。当前是本地 SwiftUI/AppKit 应用，不存在本次需要重建的远端后端。系统指标与应用统计走两条相关但不同的路径，后者是本次准确性缺陷的集中处。

```text
MonitorStore
  ├─ 系统新鲜观测 → StatisticsRecorder → 分钟/小时/日 StatisticsDatabase
  └─ 每分钟进程采样 → StatisticsRecorder.recordProcesses
       ├─ StatisticsProcessStore → 应用日聚合/身份图标
       └─ ProcessAlertCenter → 内存事件/通知/设置页
后台快照 → ReportDataAggregator → NativeReportViewModel → 原生报表
快照 → StandaloneHTMLReportExporter → HTML / 瞬时 WebKit 打印
```

初始证据、缺陷定位与已运行测试见 [reference/baseline-review.md](reference/baseline-review.md)。这些是 2026-10-01 快照，实施前需核实最新分支与工作区。本文后续内容是目标设计，不是已实现事实。

约束：最低 macOS 15；经典毛玻璃；现有 MonitorPalette 与共用布局令牌；沙盒和渠道边界；无数据不补零；统计开关和隐藏期门控；保留使用打卡与图标历史；未授权提交。旧 `openspec/project.md` 的 Liquid Glass 产品描述已落后于本轮 AGENTS.md，采用后者的经典材质决策；旧 spec 中无关窗口尺寸/四指标限制不在本次改写范围，按当前源码判断，不扩散整改。

## Goals / Non-Goals

**Goals:** 让用户不理解档位图也能判断系统状态；摘要可一路追溯至对应事件；每个值有单位、分母、有效区间及来源质量；重启、睡眠、失败和旧库都保持可信；接手 Agent 能分阶段交付并独立复现验收。

**Non-Goals:** 不诊断硬件健康或把高占用等同故障；不自动终止应用；不推断具体应用导致压力的因果关系；不引入新权限、云同步、全进程每秒长期存储、全局材质实验；不重写无关菜单栏/面板运动链路；不把既有摘要删到空洞。

## Decisions

### D1. 一个指标契约，区分量、率、占比与压力

新增共享纯数据定义（候选名 `StatisticsMetricDefinition`，名字可调整）：指标 ID、canonical unit、百分比分母、关注门槛、分布边界、展示格式、有效观测最大间隔及版本。采集使用原始值；状态机和聚合读取同一定义；UI/通知/HTML 只做展示。禁止在 SwiftUI 标签中复制档位数字。

| 指标 | 存储/计算 | 展示与门槛默认 |
|---|---|---|
| 应用 CPU | single-core percent + 实际区间；跨线程/进程合并按现有采集归属 | 100% 表示一个逻辑核，可大于 100%；不要称 >=80% 为整机满载。保留 30/50/80 档位为占用区间，60% 为候选关注门槛；详情给出基准与核数 |
| 应用 GPU | 有效来源的利用率和区间 | 核实当前来源的分母/多进程归并；40% 候选门槛、20/40/70 分布只在基准可解释时保留。不可解释的比例不写成整机份额 |
| 应用内存 | bytes，使用当前可验证的内存来源类型 | 用 GiB/MiB 表示二进制容量；分布沿用真实 1/2/4 GiB 边界，最高段为 4 GiB+，不叫“严重”。候选关注门槛为 max(3.5 GiB, 物理内存×20%) |
| 网络 | rateBytesPerSecond 与 intervalBytes 分开 | 网络速率和累计流量统一十进制 MB/s、GB；旧 20 MiB/s 门槛按原始 bytes 转为约 20.97 MB/s，不因改单位暗改原始门槛；分布 5/20/50 MiB/s 同样换算生成标签 |
| 磁盘 | read/write bytes 与实测区间 | 累计 GB/TB，速率 MB/s，采用十进制；日常卡片精度收敛，详情可增加小数 |
| 系统压力 | 系统原生内存/热档位、有效观测秒数 | 压力状态来自系统信号；使用率、驻留内存量和压力不是同一指标 |

容量相关门槛是本次设计默认，不是此前的已测结论：8/16/32/64 GiB 设备分别测试，物理容量未知时使用绝对门槛且标记无法计算份额。这只是中性“值得查看”的关注信号，不触发严重压力语气。是否通知由 D4 的通知政策决定。GPU 数据来源、CPU ps 时间口径必须实施前核实；若来源不是当前采样窗口均值，积分改走可验证累计时间差分，不能仅在旧值外包一个时间权重就声称准确。

所有二进制容量显示 GiB/MiB；所有流量/吞吐显示 GB/MB/s；同一指标在四个表面必须一致。字节边界保留精确原始值，舍入只发生在显示层。避免以一种含混“GB”同时表示两套除数。

备选：只改错误字符串最省事，但不能防止下一次阈值漂移；将所有数值换成整机百分比会丢失应用 CPU 可跨核的有用信息，因此保留正确基准并解释。

### D2. 时间范围与数据质量共用模型

共用 `StatisticsTimeRange`（候选名）解析为包含 capturedAt/calendar/timeZone 的 `[from,to)`。今日=今天零点至快照；近 7/30 日=含今天的 7/30 个自然日；近一年=含今天的 365 个自然日。日期选择结束日转换为下一自然日零点；未来部分裁到 capturedAt。自然日推进用 Calendar，不用固定秒数。

设置入口传递 committed range 与 app/metric/event 锚点。已经打开的报表通过新请求应用上下文；仅刷新保留现有范围和页面。UI 标题展示已提交结果的区间，后台计算期间不能把新标题配旧数据。

每份统计结果携带 coveredSeconds、有效区间/可用粒度、来源质量和最后更新时间。质量至少包含：本期有效、部分覆盖、仅旧日汇总、前列样本估算、无有效观测、来源不支持；这些可组合，不用一个 boolean 混淆。缺少观测是缺失，不能当作真实零。

部分日范围：新数据用细桶及有效区间裁剪；旧日汇总不能精确拆分，禁止按比例伪造小时数。只有完全位于查询区间内的旧日桶可进入本期汇总，边界日不能混入精确总量；应用页注明边界覆盖不足。如提供整日参考，必须独立于本期汇总并显示实际整日范围，不能自动扩展本期日期。默认自然日预设避免制造多数不必要的部分日查询。

### D3. 有效区间与事件状态机

采样结果强类型化，包含 source/metric/appID/processIdentity、sampledAt、区间端点、值、来源成功/失败、覆盖质量。进程标识至少 PID + 启动身份，防止 PID 复用；应用指标需先按稳定应用归并，同一应用同一指标同一有效区间只摄入一次。网络和其他指标分批回调只能更新本次实际包含的维度，空数组不是其他维度的恢复证据。

60s 仍为后台默认排期，不新增全量每秒扫描。窗口平均来源遵循来源提供的真实覆盖范围；瞬时值的区间累计要求相邻有效观测都高于门槛且间隔可接受。缺少来源区间时，两次 t=0/60s 瞬时高值最多证明估算覆盖 60s；首个瞬时样本为 0s，不凭空记一分钟。事件资格仍默认累计连续有效 120s，不能把“两次采样”误作两分钟。用于瞬时证据的默认 maxGap=90s，独立于有明确区间的来源；越界即断开，不插补。

纯状态机输入：有效高值、有效低值、未知/失败、未入榜、退出、睡眠/关闭记录/重启、时钟异常。输出：状态更新、结束原因、可持续化记录、待发通知意图。副作用在中心/store 中执行，不在计算核心中执行。

| 情形 | 行为 |
|---|---|
| 首个有效高值 | 建立候选，不增加不存在的前序区间；先判旧事件断点再处理新样本 |
| 连续有效高值 | 在有效覆盖内累计，达到 120s 才列入确认高占用 |
| 有效低于门槛 | 按观测语义结束高区间，确认恢复；结束点不外推到缺失时段 |
| 未入榜 | 标未知；对已触发关注的应用做有界定向复查，复查失败不能宣告恢复 |
| 失败/来源失效 | 暂时不累计；超 maxGap 后以中断结束，显示缺失原因 |
| 进程退出 | 终结该进程证据；应用其余进程仍存在则重新计算，不由单个 helper 退出宣布应用恢复 |
| 睡眠/关闭记录/重启 | 以中断终结连续事件；唤醒后建立新基线，禁止接到旧事件 |
| 时间倒退/重复帧 | 去重、不累计负时长；无法确定连续性时中断 |

存储字段区分：eventSpan=首末观测跨度、highObservedSeconds=有效高占用区间并集、continuousHighSeconds=本连续段有效高占用时间；均值=sum(value×validSeconds)/sum(validSeconds)，峰值只取有效样本。档位秒数覆盖只针对有效区间，与高占用秒数一致；多指标同时发生，应用级总时长用区间并集，不能相加。

新的样本峰值不冒充真实瞬时峰值；显示“采样峰值”。缺失时保留上次有效值必须配“最后观测于…”而非“当前”。事件可查到恢复/中断状态，候选未达持续门槛不计为一次确认事件。

备选：仅修 durationMinutes 不能解决 false recovery；沿用 150s 无输入即恢复无法证明恢复；无观测一律补零会掩盖采样失败，因此采用显式状态机。

### D4. 高占用、系统压力与通知政策分离

正式界面采用“资源占用较高/持续较高”等中性语气，真实系统内存/热压力用现有 warning/critical 语义。占用再高也不能仅凭绝对值宣告“造成系统压力”。同期系统压力可以在详情展示“同一时段出现内存压力”，不能写确定归因。

保留用户现有总通知开关与授权，不新增权限申请。系统压力通知沿现有中心；应用通知默认在确认高占用事件且同期有有效系统内存/热压力时才发，普通高占用留在界面。每应用每事件合并多个指标、首次符合条件一次，随后只有明确系统严重度升级才再次提示；缺失或中断不是恢复通知。描述写占用、覆盖时长和同期状态，使用统一单位。发送失败不把 notified 标成成功；可有界重试但不能通知风暴。

不用“少量高占用就是故障”的备选政策。固定严重度条会误导，所以默认行移除档位颜色条；详情中分布图表示量级分布而非风险等级。

### D5. 身份、细桶与持久化

应用身份优先 bundle identifier，显示名称仅作标签；系统进程以可稳定验证的可执行身份/路径类别为键；拿不到稳定身份时使用明确标识为 unresolved 的会话进程键，不按同名自动合并。不要把 PID 当长期主键，也不要跨 PID 复用串接。

候选数据模型：`AppIdentityV2`（stable ID/display name/icon/aliases/quality）、`AppMetricBucket`（interval、有效秒数、weighted sum、peak、tier seconds、quality/version）、`AppResourceEpisode`（UUID、应用/指标、起止/最后有效时刻、状态/原因/区间、notification state/version）。现有 `StatsAppDaily` 继续承载旧聚合；新 schema 通过明确迁移接入，不能假设 SwiftData 自动推断一定成功。

保留期默认沿当前应用历史上限：细桶及事件 60 个自然日，日汇总继续遵循既有策略。按实际采样形成细桶，保存裁剪必要的有效区间/段，不能只存分钟标量又宣称任意部分分钟精确。负载分布保留量级秒数；每个事件查询范围内指标按段裁剪后重算，不按整个事件时长简单比例缩放峰值/均值。

队列负责所有上下文访问，MainActor 只发布不可变小快照；事件存储不在每次 body 求值里查询。应用关闭/终止前尽力保存已确认事件；不能假设 MainActor 同步图标查库始终便宜，应移至身份快照或共享缓存。支持多实例时查询与写入事务去重，且应用实例竞争不能使事件倍增；实施前核实两份同 Bundle ID 进程同时运行的写入策略。

旧身份按名字存储且无法可靠恢复 bundle ID：保留 legacy-name 标识，只有可证实映射才建立 alias。同名映射冲突不合并。旧日汇总、旧样本次数档位保留并标“旧版按采样次数估算”，不把旧记录转换成新精确秒数；此前只存在内存的事件无法追回，不重建成历史事实。

落库失败保留可重试状态与原库，不吞错；重启把持久化 ongoing 以最后有效覆盖端点标为 interrupted，不延长到启动时刻。删除范围/清空应用统计同步处理事件、细桶、缓存、日汇总与当前状态，禁止在途旧任务把删除的数据写回。使用打卡按原语义保留；双渠道数据目录独立。

备选：只保存 daily 不支持准确范围和事件详情；保存全进程每秒明细代价高；新桶只记录现有前列和少量定向复查，仍说明未覆盖全部应用。

### D6. 设置摘要的目标画面

页面保留原生设置分组。默认顺序：记录/通知控制 → 历史范围和结论 → 当前应用关注摘要 → 核心用量/传输 → 查看完整统计 → 存储管理。设置页面不是第二个完整报表。

```text
数据统计
记录统计                         [开关]
异常通知                         [开关]

[今日 | 近7日 | 近30日]                   [查看完整统计 ↗]
所选时段：系统压力较低
有效记录  …                         数据完整度 …

当前资源占用                 2 个应用较高       [查看全部 ↗]
[Safari图标] Safari              内存 5.8 GiB          [▸]
[系统图标] WindowServer          GPU 46%               [▸]

用量：CPU / GPU / 内存 / 功耗
传输：网络 / 磁盘
存储管理 →
```

数值只是示意，不能用作真实采样夹具。当前状态与历史结论在空间/文案上分开；历史平均与当前值不要在一句话里拼成隐含同一时间。

默认最多 2 个应用行；标题始终说明总数，查看更多进入完整应用列表。主要指标选择当前超门槛的相对程度最高者，跨量纲只比较 value/threshold；排序在同一数据刷新提交时稳定：有效且同期系统压力的事件优先 → 相对程度 → 有效连续时长 → stable ID。不得把“同期”叫“致因”。更新不因小数噪声频繁重排行，实施时使用稳定排序/刷新提交，不常驻动画。

同一应用多个指标合并到一行，主指标后可加“另 1 项”；按行 disclosure 展开：采样均值、采样峰值、开始/最后观测、有效持续时间、状态/覆盖原因、“查看此应用详情”。档位条、所有事件列表与原始数据不默认铺在设置页。默认及一个行展开时，以当前设置窗口实际可用高度检查报表入口能否容易找到；不得为塞入内容缩小到原来的 9.5pt 小字或强行截断关键事实。

使用已有字号体系、MonitorPalette、SettingsGroup/Divider；减少灰色容器套娃，最多分组底座与展开内容两级。正常高占用保持中性色/提醒色，系统严重状态使用已有严重度令牌；无意义彩条、零时长图例、重复警报标题移除。图标优先真实应用、WindowServer=display、其他=terminal。名称长时保留全文 tooltip/可访问性，不缩放数字；单位对齐、monospacedDigit，不用运行时测量修布局。

### D7. 完整报表形成可追溯链路

扩展现有报表打开上下文，不只 `.apps`：range + module + appID + metric + eventID；首次开窗和已有窗口都应用。事件可能已恢复/删除时，展示历史事件或明确“记录已不存在”，返回正确范围的应用页，不静默换成 CPU 榜首。

应用模块默认可比较排行：应用、观测均值、采样峰值、有效高占用时间、估算累计消耗/总量；按指标切换列含义。CPU 累计核·时是有效观测估算，不是使用电脑时间；内存累计不强造“核·时”。列表保留榜首摘要但提供完整已记录列表、排序与搜索，空结果/清除搜索/系统进程过滤行为一致，系统过滤也作用于事件展示或明确事件独立过滤。技术身份不重复显示在普通行，只在详情可复制。

应用详情使用现有原生报表容器的二级 detail/inspector（以窗口宽度选稳定布局），包含本期来源与覆盖说明、指标趋势、事件列表；事件详情显示原因、状态、起止、并集有效高占用时长、档位分布、均值/峰值及同期压力。事件单条计数与“出现几次”基于事件 ID；一应用多指标事件不混写成多次应用故障。时间线标中断，分布条标“有效观测时长分布”，零段隐藏，有文本兜底。

总览首位是时段结论+有效记录/完整度；压力评分保留为辅助“系统压力评分”，评分依据说明只评估已观测内存/热状态，不能称整机健康或硬件寿命。无评分时说明原因，不显示100。系统状态、历史摘要、当前应用关注数各有标签。

默认趋势先显示 CPU/GPU 两条，选择“内存”切换到内存占用/系统压力视图；可启用更多曲线但每条有完整单位/基准，不因同为百分比暗示指标可加或相等。既有热力图、P/E 核、GPU/内存、电池/功耗、传输、热状态、洞察、原始表和硬件档案保留，各页仍回答独立问题。

历史统计是明确标有 capturedAt 的快照；当前右栏单独标“当前”，只刷新当前模块。刷新保留范围、选中应用/事件、用户排序和可恢复的滚动位置；不宣称快照在每秒更新。

备选：用新首页替代所有模块会牺牲有用内容；仅调整字重不能修补无事件详情的导航断点。

### D8. 分阶段加载与交互性能

先后台读取统计与事件并发布可读报表，硬件清单以独立任务补充，失败只影响硬件区。沿用共享 SystemProfilerRunner 缓存和有界并发；不要为每次范围切换重跑探针。统计请求、范围聚合与硬件请求分别使用 generation，避免共用一个 requestID 互相使结果失效或留下 loading。取消检查贯穿耗时阶段与发布；关窗后任何任务不能重建 UI 或计时器。

首屏不等硬件，但需硬件事实才能判断的指标先显示未知，不短暂假造“无电池/无风扇”。数据未载入时保留布局与明确状态；失败可重试并保留已有成功快照，标题仍对应旧快照。减少重复图标解码和全页 ObservableObject 无关刷新；复用已有图标缓存，测量后才决定重构力度。

在同机同数据库记录打开→首个可读结果、冷/热硬件缓存、范围/模块切换、长列表/悬停、关窗/隐藏资源。慢硬件测试夹具下统计结果应在硬件完成前出现；真实交互保持或改善基线，不能把后台 CPU 下降当作滚动/动画通过。若数值基线没有历史记录，先测基线再写目标，禁止杜撰 p95 改善。

### D9. 导出与设计文档保持同源

从 committed snapshot/rangeModel 导出；HTML 可独立切换范围，但必须使用相同原始单位、时间边界与质量语义，不能继续让旧 JS 算法覆盖新 Swift 结果。优先注入共享聚合产物/版本化数据合同，确有必要保留 JS 重算时用金标准 fixtures 验证等价。打印当前选择的范围/应用上下文，页面标范围、更新时间、来源限制；打印不依赖尚未完成的硬件读取。保留沙盒保存对话框、失败提示与临时 WebKit 清理。

实施 UI 前建立/补齐项目 DESIGN.md（本轮不修改全局设计文件）：记录本变更获批的层级、经典材质、模块图标与“高占用不等于压力”文案原则；引用现有运行时令牌，不复制参数表。扩展已有原生报表 UI contract，而不是另建 Web 交互规范。正式示例入口删除/迁往 DEBUG 独立 fixture，不能写入共享真实状态。

## Risks / Trade-offs

- 前列采样不等于完整应用资源账本 → 说明样本均值/估算；定向复查仅追踪少量活跃关注应用，仍受渠道可用性约束。
- 旧日汇总不能拆到任意小时 → 保留旧值与质量标签，明确实际整日范围，不按比例伪造。
- 新 schema 的失败/回滚可能损坏真实历史 → 测迁移副本、幂等版本、保存成功后再切换，保留兼容旧日数据；不提供“迁移失败就清库”兜底。
- 60 日细桶与段可能增加存储 → 有界写入、按时间索引/查询，测 60 日夹具占用与维护耗时；不全量每秒落盘。
- 定向复查增加探针负载 → 共用批量来源，一次样本按原排期；设并发和关注集合上限，不挤占面板2s游标，不借机扩大权限。
- 两个同 Bundle ID 实例可能重复记录 → 接手时先检查实例/写入协调；事务幂等，必要时单写入租约。
- 压力与占用相关不能证明因果 → 所有描述限制为同期，WindowServer 不默认建议用户关闭。
- 部分正式语言/硬件难以实测 → 不标验收通过，记录 fixtures 与实机验证边界；不通过删内容降低验收。

## Migration Plan

1. 固化基线和 golden fixtures；优先实现共享单位/范围/采样输入修复并测试，尚未有新事件库时不声称历史完整。
2. 稳定身份和 V2 状态机以隔离测试数据验证，定义 schema 与旧数据质量映射，完成迁移/失败恢复，再切正式采样。
3. 新数据保存细桶/事件、秒数累计；保留旧日聚合读取。避免新旧重复计入：range query 按数据版本与时间覆盖选择明确来源。
4. 接通详情/上下文/导出，之后切换设置摘要与总览；各阶段单独构建、实机验证，不能先改文案把错误数据包装成可信数据。
5. 完成双渠道、语言/外观/窗口矩阵、迁移/休眠/失败和性能证据；保留任务勾选与验证文件一致，用户未授权不提交或发布。
6. 回滚先停新写入，旧 app 只能读取它兼容的库/模型。不得要求老二进制直接打开不兼容 schema；使用实施前保存的迁移副本恢复旧版本验证，明确新版本数据不会被静默丢弃。若新库并存，应保留新库而不删；合并/迁移路线在任务 3 的 schema 文档中具体写明。

## Open Questions

仅剩不改变规范的实现核实：GPU 可验证分母、CPU 当前采集实际窗口语义、SwiftData 可行迁移步骤、现有字体/令牌与滚动容器的复用位置、基线硬件探针耗时、当前 catalog 的既有语言集合。处理方法和失败语义已在上述决策中定义；实施者将实测结论补入 reference/verification.md。若证据使能力无法实现，记录明确限制和修订原因，不擅自把估算标成精确或扩大权限。
