# 数据总览：评分评估与三版原型

入口：`index.html`。A 状态摘要（推荐）、B 时段分析、C 指标总览，通过顶部标签逐版查看。支持三个时间范围、深浅色、数据不足场景、口径说明弹窗。全部是演示数据，不读取本机数据库。正式 SwiftUI 页面与评分实现未修改。HTML 仅验证信息结构与交互，不代表原生材质验收。

## 对现有评分的判断

方向有基础，但目前更像“加权资源应力指数”，不能称作健康时间占比，更不能代表硬件健康或实际流畅度。

依据：`HagimiMonitor/Statistics/StatisticsHealthScore.swift`、`StatisticsDatabase.swift`、`StatisticsRecorder.swift` 与 `Views/Settings/StatisticsSettingsView.swift`。

1. 当前公式为 `100 × (1 − 0.45M − 0.30T − 0.15C − 0.10G)`。CPU 超过 85%、GPU 超过 90% 线性扣分；只有这两项满应力、内存和热状态正常时也只有 75 分。这与“高负载不扣分”的注释和产品意图矛盾。峰值不直接参与评分，但在总览占据突出位置，容易进一步误导。
2. 应力百分比是严重度加权均值，不是真实异常时间比例。例如 CPU 在 92.5% 持续整个窗口，CPU 应力是 50%，并非只有一半时间处于高负载；热 fair 整段对应 20% 应力，也不是 20% 时间“过热”。应力不能乘覆盖时长后标成异常分钟。
3. 热应力达到 1% 时，优秀评级被限制为良好，而分数不变，产生截图中的“97 分／良好”。代码软帽注释提到约 2% serious，但当前映射是 serious=0.6，对应约 1.67%；fair=0.2 也能触发。将提示一概称作“过热时长”不准确。
4. 缺失维度按零惩罚且不归一化，只有 CPU 时也可能得到 100 分；入口还要求存在 CPU 信号，即使有其他有效维度也可能不评分。缺失应影响可评分性与完整度，不应该看起来更健康。
5. 评分和跨桶均值按帧数 n 加权；coverS 已表示墙钟覆盖，但不是各维度有效观测时长。不同采样节奏、不同维度缺失率会影响可比性。直接换成 coverS 加权仍不足以修复桶内缺失和节奏偏差。
6. 帧级先算非线性应力再汇总，是值得保留的设计；旧历史用均值回退应明确标记近似，不能与新口径无提示混合。

## 推荐模型

优先采用 A：取消总览大分数，展示“系统状态 + 真实压力时长 + 工作强度 + 记录范围”。不把检测不到压力称作已经证明流畅。

如需保留分数，C 可使用下列候选模型进行验证，而不是直接发布为已校准体系：

- 名称采用“状态评分”。CPU/GPU 使用率移出扣分，仅呈现工作强度。
- 内存与系统热状态各自计算严重度加权有效秒数 / 对应有效观测秒数。原始档位时长同时保存，避免只保留不可逆的总应力。
- 候选公式 `100 × (1 − 0.6 M − 0.4 T)`，其中 M 可暂用 normal/warning/critical = 0/0.6/1，T 暂用 nominal/fair/serious/critical = 0/0.2/0.6/1。权重与级别映射是待校准产品假设，不是 Apple 定义的评分规则。原型 C 演示数字不构成评分器实现或模型验证。
- 分数显示长期总体负担；严重事件独立提示，避免平均值稀释风险，也避免暗中修改等级。分数等级只由同一公开区间映射。
- 两核心维度缺一时显示“数据不完整”，不出完整总分。各维度展示有效记录时长；无已知应观测时长时不声称“覆盖率 100%”。少量样本显示“数据不足”。最低样本门槛和稳定性需用真实记录验证后决定。
- 温度回退作为“温度提示”，说明来源；不要将固定 85°C 阈值当跨机型统一健康裁定。不把热压力等同于已证实降频。
- 评分按版本保存口径。旧数据无法重建新状态秒数时维持旧口径或显示不适用，不能制造回溯精度。

## 可增加的维度与边界

| 维度 | 用户能获得的信息 | 是否计入评分 | 当前数据与新增工作 |
|---|---|---|---|
| 内存压力 | 警告/严重累计时长、最长连续时段 | 核心 | 已有帧级档位参与应力；新增档位秒数、有效秒数与事件摘要 |
| 系统热状态 | serious/critical 时长与出现时间 | 核心 | 已有状态参与应力；新增档位秒数，不能用温度均值代替 |
| 计算工作强度 | CPU/GPU 高负载累计、分布 | 不扣分 | 已有利用率均值/峰值/应力；阈值秒数与直方图需新增 |
| 压缩与交换 | 平均压缩和交换占用；压力背景 | 解释项 | 均值已有；换页速率需新采样，不把 swap 占用当交换速率或单独故障证据 |
| 功率与耗能 | 负载背景、记录期间能量 | 不直接扣分 | powerAvg 已有；准确能量需按传感器有效时间积分，先核对功率边界，不称任务能效 |
| 网络与磁盘 | 下载/上传、读写量及趋势 | 不扣分 | 总量已有；不以字节量判断网络质量、磁盘寿命或 I/O 阻塞 |
| 同机历史变化 | 压力负担较自身基线变化 | 解释项 | 需要同口径历史窗口；按有效小时、工作强度和供电场景比较，不能对不完整今日与完整昨日直接比总量 |
| 响应性与 I/O 等待 | 实际交互延迟、排队或换页阻塞 | 未来验证后考虑 | 当前统计列不足，需专门探针与两渠道可用性验证；不能用 CPU 满载推导 |
| 电池健康 | 长期硬件状态 | 独立档案 | 与时间窗口运行状态分开；不让台式机或无电池设备受影响 |
| 数据完整度 | 这个结论依据多少观测 | 评分门槛 | coverS 已有；需要每维度 valid seconds、缺失原因与旧数据标记 |

Apple 将内存压力解释为多个因素共同决定，包括可用内存、交换速率、wired memory 和文件缓存，而非仅内存占用百分比：[Apple 内存监视说明](https://support.apple.com/en-euro/guide/activity-monitor/-actmntr1004/mac)。系统热状态有 nominal/fair/serious/critical 档位：[Apple ThermalState](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum)。上述评分公式与设计取舍为本项目建议，并非 Apple 的健康评分标准。

## 三版取舍

- **A 状态摘要**：首屏回答“要关注什么”，三项关键指标加紧凑资源行。适合现有设置页，是推荐落点。
- **B 时段分析**：图表与关注时段优先，适合从 A 进入详情。事件详情中的负载只是同期现象，不归因到某个应用。当前进程统计不能据此直接生成事件级因果关系。
- **C 指标总览**：保留数字评分，七个维度放进同一表格，比原六卡片更紧凑。适合用户仍重视分数的方向，但需要先解决模型可解释性。

## 落地顺序与验收

1. 确认布局方向；可以 A 作为设置总览，B 作为详情，而非将三版同时塞进产品。
2. 先移除峰值、修正文案、展示覆盖和已有压缩/交换/用量。不要提前输出异常分钟数。
3. 增加每维度有效秒数、状态秒数、高负载秒数及事件合并摘要。处理睡眠、暂停、采样中断、跨桶与跨日边界；明确连续事件的去抖与结束规则。
4. 用轻载、满载但状态正常、内存压力、热压力、缺维度、无数据、睡眠间隙、长短采样节奏等夹具验证。满载但核心状态正常应不扣分；缺数据不出完整高分；分/时/日汇总的时长结果应一致。
5. 若增加 P95，需原始样本或可合并直方图/草图；现有均值和峰值不能恢复真实 P95。若只用分钟均值计算，应明确命名“分钟均值 P95”。
6. 正式 SwiftUI 落地再验证两渠道、明暗外观、主题配色、最坏标签宽度与原生滚动材质；这次原型不作为这些项目的验收。
