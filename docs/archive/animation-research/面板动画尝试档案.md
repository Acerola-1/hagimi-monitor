## 1. 用户想要的（验收定义）

1. **任何设备上都流畅**：面板行展开/收起动画在 60Hz、75Hz、120Hz、144Hz、电竞高刷屏、省电模式（降频）下都必须流畅。同一套逻辑，发挥每台设备自身的潜力。
2. **视觉效果保持现状**：用户明确表示喜欢当前的内容展开/收起效果——非线性弹簧节奏、内容自上而下卷出（内容静止、揭示边界下移）、下方行平滑推移、快速连点时中断保速度续接。**曲线、时长、方向、中断行为全部不许变。**
3. **不做绑定帧数的补丁式优化**：针对特定帧率调参数在用户看来是诡异的工程设计（用户原话大意：本就不该绑定帧数做优化，应该优化 SwiftUI 本身，让逻辑通用）。
4. **面板与内容是同一个面（2026-08-30 追加，逐帧不变量）**：内容高度变化时面板必须紧密跟随。可检验表述：**动画进行中的每一帧，面板底缘与内容最后一行可见边缘的间距都必须恒等于收尾间距（10pt）；任何一帧这个间距变大或变小都是错的。** 同理，被 toggle 行的揭示边界与下方第一行顶缘的间距（6pt）在每一帧都必须恒定。「两个运动最终到达同一位置」不算合格——它们在每一帧都必须重合。

## 2. 工程已做的尝试与结果（均未达到目的）

### 第一版：同参弹簧跟随（`7f4717fe`，已在 dev）

- **做了什么**：窗口层弃用异参 CA easeOut，改由 `PanelWindowSpring` 以与内容同参数的弹簧在 CADisplayLink 上跟随窗口终高。
- **结果**：修复了"窗口与内容动画曲线异相（分段跳变）"这一具体缺陷，但整体卡顿依旧——它没有触碰性能瓶颈。
- **用户目测**：该节点构建版本"也变卡"。

### 第二版：displayLink 帧率请求（分支 `feature/panel-expansion-perf`，已撤销放弃）

- **做了什么**：给 `PanelWindowSpring` 的 CADisplayLink 设置 `preferredFrameRateRange(60, 240, preferred:120)`——此前无帧率范围，被系统压在 ~60Hz。
- **结果**：120Hz 主屏上手动测试变流畅了（实测弹簧帧间隔从 16-37ms 抖动变为稳定 8.3ms@120Hz）；**但 60Hz 屏上完全无效**——60Hz 屏本来就不存在 cap，这个请求等于无操作。用户目测："60Hz 的屏幕上卡得完全无法跟其他软件相比"。
- **结论**：只修了窗口层的贴合频率。

### 两版的共同问题

都只优化"窗口底部边缘的贴合频率"这类**外围**，而动画卡顿的真正根源——**内容层动画的逐帧主线程布局**——从未被修改。用户对第二版的提问一针见血："修改中难道有跟帧数强关联的东西吗？为什么 60Hz 上卡的完全无法跟其他软件相比？"

## 3. 根因（现状代码分析，基于 dev 52cd1078）

> **2026-08-30 实测修正**：本节的布局侧分析在方法论上成立，但第三版实装后的对照实测表明，本机（Mac mini M4 + macOS 26 RenderBox）动画期主线程的真正瓶颈在**渲染侧**（可见变化面积的逐帧重渲染），不在 SwiftUI 布局——详见 §10。本节保留作为分析过程记录。

### 3.1 内容层：逐帧主线程布局

`MonitorPanelView.swift:2945` `CollapsibleDetail` 的展开/收起：

```swift
.frame(height: expanded ? contentHeight : 0, alignment: .top)
.animation(.spring(response: ..., dampingFraction: ...), value: isExpanded)
```

SwiftUI 对 `frame(height:)` 的动画是**逐帧主线程布局**：一行展开区高度每帧变化 → VStack 内所有下方行的位置、每张行卡片的玻璃材质（`compatibleGlassEffect`）逐帧全图失效重算。

### 3.2 为什么两块屏表现天差地别

逐帧布局提交耗时接近 **16.7ms（60Hz 帧预算）**：

| 环境 | 后果 |
|---|---|
| 60Hz 副屏 | 提交耗时贴着帧预算 → 掉帧到 30fps 以下 → 灾难 |
| 120Hz 主屏 | 掉帧后有效帧率仍有 60-80fps，观感被掩盖（"还行"） |
| 120Hz 主屏 + 省电模式 | 系统降频到 60Hz → 等价 60Hz 工况 → "省电模式更明显" |
| autotest 自动展开 | 大行程、弹簧初速快，掉帧被掩盖 → 表面"非常流畅" |

### 3.3 瓶颈确认的历史实证

2026-08-28 曾做过"分段刚性位移"改造：把逐帧布局改为纯变换后，**动画窗口主线程负载 -43%、慢帧 10→1.6**——证明瓶颈确实在逐帧布局本身。该代码未提交且 worktree 已删，不可恢复，本计划是重做。

### 3.4 窗口层现状（正交，不在本计划范围）

`PanelWindowSpring`（`HagimiMonitor/Views/Panel/PanelExpansionDriver.swift:183`）用 CADisplayLink 闭式解弹簧逐帧贴合窗口高度，与内容弹簧同参数（第一版成果，保留）。第二版的 `preferredFrameRateRange` 修复在 120Hz 屏上被验证有效，**实施本计划时应一并重新应用**（窗口层仍需要它，否则 120Hz 屏上窗口底部会半速阶梯）。

## 4. 解决办法：布局一次落终值 + 合成器侧纯变换

**原则：SwiftUI 布局系统只在动画开始与结束各计算一次；中间所有可见运动由 Core Animation 对图层变换（offset/opacity/mask position）插值完成——合成器逐帧，主线程零逐帧布局。** 这与帧率天然解耦：刷新率越高插值越细，主线程工作量恒定。

三个视觉子效果各自的无布局实现（视觉与现状等价）：

**① 展开区内容的"卷出揭示"**（内容静止，揭示边界自上而下扫过）：

```swift
// 布局瞬时落到终值 h;视觉上白色 mask 从 wrapper 上方(offset -h)滑入覆盖(offset 0):
// 揭示从上到下逐行出现,内容自身完全静止——与现 frame 动画视觉等价
content
    .mask(alignment: .top) {
        Rectangle().frame(height: h).offset(y: maskOffset)   // -h → 0,纯变换动画
    }
```

mask 是独立图层，offset 动画由合成器插值，主线程只在首尾各提交一次。

**② 下方所有行的"推移"**：布局瞬时落终值后，对"被 toggle 段之后的所有兄弟段"整体施加反向补偿再归零：

```swift
Group { /* 被展开段之后的全部段 */ }
    .offset(y: compensated)   // 动画: -(Δh) → 0,纯变换
```

一次 toggle 多段（全量展开/默认展开设置）时 Δh 为各段自然高度之和，同一补偿组仍成立。

**③ 透明度**：`.opacity(expanded ? 1 : 0)` 保持——opacity 本来就是合成器属性。

**弹簧与中断**：offset/mask 动画用与现版**同参数**的 `withAnimation(.spring(response: MonitorConstants.panelExpansionSpringResponse, dampingFraction: ...))` 驱动（参数从 `Constants.swift` 读取，不改值）；SwiftUI 动画对变换属性天然支持中断重定向（保速度续接），观感与现状一致。

1. **段结构重排**：把 `MonitorPanelView.swift:92` `ForEach(store.modules)` 的"行卡片（内含 CollapsibleDetail）"组织为段模型（行头+其展开区）；按"被 toggle 段的前/后"分组，为 ② 的补偿容器做准备。`expandedKinds`/`toggleExpansion`/`setExpansion` 对外语义不变。

## 6. 验收标准（可量化）

1. **视觉等价**：120Hz 主屏上新旧实现并排录屏逐帧比对，弹簧轨迹、揭示方向、时长无可见差异（用户主观确认）。
2. **60Hz 达标**：60Hz 副屏（或省电模式）手动点击展开/收起，底部边缘与行推移平滑，"一顿一顿"消失（**用户手动目测是最终验收**）。
3. **主线程指标**：autotest 度量窗口内 `main` CPU 时间较改前下降 ≥30%（对标历史实测 -43%），`slowframes` 接近 0（改前 10/动画）。
4. **功能回归**：全量测试通过；快速连点中断/重定向无相位错拍；面板封顶滚动、点击命中、玻璃材质无回归。
5. **帧率无关性**：同一构建在 60Hz/120Hz 屏上代码路径一致，无任何按刷新率分支。

## 8. 风险与回退

- **mask 动画的下沉程度**：SwiftUI mask 的 offset 是否完全合成器插值需实测（对比改造前后 autotest `main` 指标）。若 mask 仍走主线程，备选：`visualEffect` 实现，或展开区内容预渲染快照 + 图层位移。
- **补偿组多段叠加**：全量展开（多段同 toggle）时补偿量合成需逐一验证；异常表现为下方行与揭示区错位，可先退化为单段 toggle 场景保优。
- **回退**：全部改动单提交承载，`git revert` 即回退；改前基线产物可随时从 dev 重建做 A/B 目测。

## 9. 第三版实装记录：panel-anim-mask-offset（2026-08-29～30，已实装）

> 实装位置：worktree `tmp/wt-panim-mask`，分支 `panel-anim-mask-offset`（基于 dev 52cd1078）。双 scheme 构建通过，autotest 全量/单行场景可跑。本节零上下文可接手。

### 9.1 方案（对 §4 计划的对应与计划外补充）

按 §4 实装。实装中发现并解决四个计划未覆盖的问题：

| 问题 | 解法 |
|---|---|
| 收起时玻璃底边必须随揭示边界上移，而玻璃形状派生自布局尺寸，与「布局瞬时落终值」矛盾 | 玻璃底板按**展开终高常驻绘制**（收起时向下溢出布局、被遮罩隐藏）；新增 `PanelCardRevealGlass`（CompatibleGlassContainer.swift），玻璃应用点从各行组件外移到面板级 |
| 快速连点中断的补偿正确性 | 段位移拆两级：J（布局跳变的瞬时反向补偿，弹簧事务外写入）+ A（剩余位移，弹簧事务内归零到 −J）；中断时 A 从表现值保速度续接。SwiftUI 语义已用 swiftc 探针实证：同一事件里事务外写入不被弹簧裹挟（逐变更事务） |
| `onChange` 回调运行在动画更新上下文，裸写布局状态继承当前弹簧事务，布局被变回逐帧补间（首测 main 无改善的根因） | 布局相位改由驱动器持有（`layoutPhases`），`snapLayoutPhases` 在弹簧事务外落位；需要瞬时的状态写入必须 `withTransaction(Transaction())` |
| 收起时整段内容瞬移出面板（用户实测发现） | 布局落终值走 onChange 链路晚一拍，首拍带着旧补偿值渲染。修复：布局相位与 J 补偿同批写入（同帧原子）；遮罩基高改锁存测量值（收起/展开态各自锁存，toggle 首拍无 stale 派生） |

遮罩形态：**固定尺寸 + 滑入 offset**（不逐帧改 mask 尺寸——那会强制整卡渲染树每帧重建，§8 预警的风险，实测证实）；形状高出台面 10 万 pt、底缘锚定揭示边界，弹簧过冲的表现与布局动画一致。

### 9.2 用户目测结论

展开视觉通过（「这可能是我看过最好的一个方案」）；**收起时不通过**：面板底缘先回到目标位置，内容随后才收回同一位置，两个运动可见地错开——见 §11。

## 10. 实测修正：瓶颈在渲染侧而非布局侧（2026-08-30）

autotest 度量（main = 主线程 CPU；同机交错 A/B，Mac mini M4 + macOS 26）：

| 场景 | 基线（dev 52cd1078） | 第三版 |
|---|---|---|
| 全量展开 | ~521ms | ~540ms |
| 单行 toggle | ~415ms | ~434ms |
| 慢帧/次 | 26~29 | 27~33 |

诊断矩阵（env 开关逐项排除）：关全部内容动画 main≈250ms（内容动画机制占 ~290ms）；再停窗口弹簧 ≈208ms（窗口弹簧仅 ~40ms）；行玻璃换静态填充无变化；滑入 mask 与 frame 高度 mask 无差别。`sample` 抓到动画期主线程热点在 `RB::DisplayList::RenderState::RootTexture::render`。

**结论**：本机动画期主线程瓶颈是 RenderBox 对可见变化面积的逐帧重渲染，不是 SwiftUI 布局。§3 的布局侧根因判定在本机不成立，§6.3 的 main −30% 验收线经此方案不可达，§3.3 历史 −43% 不可复现。真正的性能杠杆是减少逐帧重渲染的材质/面积（如降低 withinWindow 毛玻璃视图数量），属视觉取舍，待用户拍板。autotest 全量展开是「整面板每帧都在变」的最坏情况代理；用户单行点击场景约为其 78%。

## 11. 目测新问题：面板与内容双时钟不同步

**现象**：收起时面板底缘先到目标位置，内容随后才收回到同一位置。

**根因**：面板底缘由 `PanelWindowSpring`（手写闭式解弹簧）驱动，内容揭示边界与行推移由 SwiftUI 隐式弹簧驱动。两者参数名义相同（response 0.32 / damping 0.82）但**是两个不同实现**，时间尺度与起始相位无保证。§2 第一版确立的「同参数 → 同相」前提从未逐帧验证过。

**用户验收的正确形式**（每帧不变量，已并入 §1 第 4 条）：动画进行中的每一帧，面板底缘与内容最后一行可见边缘间距恒等于收尾间距；揭示边界与下方第一行顶缘间距（6pt）每帧恒定。「最终到达同一位置」不合格。

## 12. 沟通与验收教训（写给后续 agent，动工前必读）

历次 agent（包括第三版实装者）反复「get 不到」用户意图的原因，不是用户表述问题：

1. **验收标准被写成了别的目标**。本文档曾把问题定义为性能重构（main CPU −30%、帧率无关、慢帧数），agent 们优化白纸黑字的指标；用户真实验收「面板与内容是一个面」此前从未写成可检验条款。**从 §1 第 4 条起已修正。**
2. **「同参数」被当成了「同步」**。「同参弹簧、全程同相」听着严谨，但两个不同实现的弹簧求解器没有逐帧验证过同相。任何「两边用同参数所以同步」的推理都必须逐帧实测后才可信。
3. **agent 看不见动画**。用户一眼看出的不同步，需要逐帧录屏比对才能发现，而没人先搭这个工具。于是「不同步」这类反馈被当成模糊形容词，用结构性改动去回应，而不是修运动关系。

**表述技巧**（用户侧）：把视觉关系说成「每一帧都要成立的不变量」（见 §1 第 4 条的写法），agent 可直接翻译成逐帧校验，不需要「看懂」动画。

**agent 侧要求**：凡改动本动画，交付前必须回答 §1 第 4 条的不变量在新实现里由什么机制保证（构造保证 or 调参近似），并实测首拍与中断重定向两处。

## 13. 下一版方向：单一时钟（panel-anim-single-clock，实施中）

**架构**：窗口弹簧成为唯一运动源。每帧由它算出窗口内容高度 x(t)，驱动器据此发布归一化进度 w(t) 与各动画段的可见高度 v_k(t)（中断重定向时以当前可见值重定基，连续性由弹簧位置连续性保证）；内容的揭示遮罩、段位移全部改为 v_k/w 的从变量，由只观察轻量时钟的小型从动视图逐帧更新（面板主体 body 不参与逐帧更新）。SwiftUI 隐式弹簧退出运动链路（仅保留 opacity 等 → 改为合成器属性不受影响）。

**同步是构造保证**：面板底缘 = x(t)，内容可见底缘 = 布局终值 ± Σv_k(t)，两者是同一个弹簧的同一数值，任何帧率下锁死。原 J/A 补偿、revealHeights 弹簧、双求解器同相假设全部移除。

## 15. 结局补记：第五版「静树直驱」（2026-09-03，已删除）

第五版按问题简报实施（worktree `tmp/wt-panim-arch`，分支 `panel-anim-arch`，提交 `733b6f13`，已删除）。架构：动画期 SwiftUI 树与 hosting 高度约束完全冻结（布局事务外落到展开态），可见运动（揭示遮罩/下方行推移/渐隐）由整幅离屏捕获裁切的 CALayer 分片承担，窗口弹簧为唯一时钟、分片几何为其标量的仿射函数。

实测达标：单行 toggle main 445→141-194ms（−58~68%）、慢帧 25-30→2-6、逐帧 gap ≤0.06pt（构造保证）、多行分片正常、封顶场景走原路径无回归；帧序列目测接装/中段/收场无闪帧无接缝。

**结局**：用户实机目测整体否决（「纯垃圾」），worktree/分支当日删除。性能与几何不变量都不是问题，出局的是**视觉本体**——离屏捕获的分片画面与实时渲染存在用户可感知的差异，整段动画期间面板观感不对。

可留存的知识：
- 瓶颈确证：动画期主线程热点在 RenderBox 对可见变化面积的逐帧重渲染，任何让显示列表逐帧演化的方案（含 mask/offset）都吃满 ~270ms/窗口；
- 窗口弹簧每帧 setFrame 只占 ~42ms/窗口，窗口级贴合本身不贵；
- hosting 层离屏渲染需要翻转坐标、contentView 层不需要；沙盒内 `layer.render(in:)` 可完整捕获 SwiftUI 树（材质呈离屏近似态）；
- 验证设施（AUTOTEST_ROW 单行场景、FRAMES 帧序列、motion gap 日志）随分支删除，如后续需要按记忆中的做法重建。
