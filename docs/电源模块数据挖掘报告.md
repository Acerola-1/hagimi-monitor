# 电源模块数据挖掘报告

> 2026-08 对 HagimiMonitor 电源（功率）模块的一次系统性挖掘。
> 方法：本机实测（macOS 27 / Apple Silicon / PD 65W 适配器）+ 开源实现交叉验证（exelban/stats、Asahi Linux macsmc 驱动）+ 互联网检索。
> 结论先行：**现有模块只用了 IORegistry 电源遥测的约 1/3 字段；"逐软件功耗"有可用的无 root 落地路径；硬件轨级拆分（CPU/GPU/DRAM 分瓦数）对普通应用已确认死路。**

---

## 一、现状盘点：我们已经挖到了什么

当前 `BatterySampler` 的数据源与字段：

| 数据源 | 已用字段 |
|---|---|
| IOPS (`IOPSCopyPowerSourcesInfo`) | 电量、充电状态、电源来源、剩余/充满时间 |
| `AppleSmartBattery` IORegistry | CycleCount、DesignCapacity、NominalChargeCapacity、Voltage、Amperage、Temperature、ChargeLimit |
| `PowerTelemetryData` 字典 | SystemLoad、SystemPowerIn、BatteryPower |
| `AdapterDetails` | Watts |
| `ChargerData` | ChargingCurrent、ChargingVoltage |
| 其他 | `IOPSCopyExternalPowerAdapterDetails`、`ProcessInfo.isLowPowerModeEnabled`、pmset 充电限制兜底 |

功率流图三节点（适配器输入 / 电池流向 / 系统负载）+ 转换损耗（差值法）已成型。
下面的挖掘结果按**获取门槛**分四档：沙盒可用、Direct 独占、需提权（不推荐）、已确认死路。

## 二、第一梯队：沙盒内直接可读（App Store 版可用）

以下全部来自 `AppleSmartBattery` 子树的 IORegistry 属性与 IOPS 公开接口，**只读、无需任何权限、每秒采样成本可忽略**。本机（macOS 27）全部实测存在。

### 2.1 PowerTelemetryData 未用字段 —— 固件级遥测的金矿

当前只取了 3 个字段，字典里其实还有 20+ 个：

| 字段 | 本机实测 | 价值 |
|---|---|---|
| `AdapterEfficiencyLoss` | 320 (mW) | **固件直接上报的转换损耗**。现在用「输入−负载−电池流」差值法推算，遥测瞬时错位时会失真；固件口径更稳 |
| `AccumulatedSystemLoad` | 552,452,170 | 开机以来系统负载能量累加器 |
| `AccumulatedSystemPowerIn` | 713,531,377,545 | 开机以来适配器输入能量累加器 |
| `AccumulatedBatteryPower` | 75,510,422 | 开机以来电池吞吐能量累加器 |
| `AccumulatedAdapterEfficiencyLoss` | 75,887,784,867,816 | 开机以来累计损耗 |
| `AccumulatedWallEnergyEstimate` | 165,179,121 | 墙插侧能量估计累加器 |
| `AccumulatedSystemEnergyConsumed` | 198,203,141,839 | 系统累计消耗能量 |
| `SystemVoltageIn` / `SystemCurrentIn` | 20053 mV / 858 mA | **实际输入电压电流**，可校验 PD 契约是否跑满（20V×3.25A=65W 上限 vs 实际） |
| `WallEnergyEstimate` | 5102 | 墙插功率估计（语义待实测确认） |
| `PowerTelemetryErrorCount` | 0 | 遥测错误计数，可作数据可信度指示 |

**累加器字段的玩法**：相邻两次采样做差，即可得到任意时间窗内的真实能量（Wh）——
「本次开机已消耗 xx Wh」「本次充电已充入 xx Wh」「今日累计损耗」都可以零成本落地，
且比我们自己积分每秒功率更准（固件积分无采样间隙）。

### 2.2 PowerDistribution —— 充电被掐断的直接证据

本机实测（充电上限维持期）：

```
IPDInputPower     = 65000 mW   IPDInputVoltage = 20000 mV
IPDInputCurrent   = 3250 mA    IPDRatio        = 100
IPDChargingAllowed = 0         IPDWattageOverride = 30000 mW
```

- `IPDChargingAllowed = 0` 是**固件明确告知"现在不允许充电"**。目前我们靠 `BatteryPower == 0`
  + 插电状态推断 maintain 态，这个字段是直接的固件证据，且能区分「充满停充」和「上限维持」；
- `IPDWattageOverride = 30W` 疑似系统给充电通路设的功率上限，与 80% 限制策略相关，值得跟踪观察。

### 2.3 ChargerData —— "为什么不充电"

```
NotChargingReason = 16777216 (0x01000000)
SlowChargingReason = 0
TimeChargingThermallyLimited = 0
```

- `NotChargingReason != 0`：stats 项目用它判定「优化电池充电已介入」（见
  exelban/stats `Modules/Battery/readers.swift`）；我们可以把 0/非0 映射成状态文案
  （"优化充电暂停中" vs "已达充电上限"），比现在的静默维持更有解释力；
- `TimeChargingThermallyLimited`：因温度限制充电的累计时长，过热保护的可观测指标。

### 2.4 AdapterDetails 扩展 —— PD 契约细节

现在只取 `Watts`，同字典还有：

| 字段 | 本机实测 | 价值 |
|---|---|---|
| `AdapterVoltage` / `Current` | 20000 mV / 3250 mA | 当前契约电压电流 |
| `UsbHvcMenu` | 5V3A / 9V3A / 15V3A / **20V3.25A** | **适配器可供协商的全部 PD 档位**——可显示"65W 适配器 · 正在 20V/3.25A 档"，小适配器（insufficient 场景）时直观展示瓶颈在哪 |
| `Description` | "pd charger" | 充电类型（PD / MagSafe 等） |
| `AdapterPowerTier` | 2 | 功率档位分类 |

`AppleRawAdapterDetails`（数组）还能看到每个 USB-C 口各自挂的适配器信息，多口插电时可区分。

### 2.5 AppleSmartBatteryPack 子树 —— 电芯级与终身档案

`collectBatteryData` 已具备递归收集能力，以下字段本机均实测存在：

**实时电芯级数据**（来自三节电芯子节点，本机 3 cell）：

| 字段 | 本机实测 | 价值 |
|---|---|---|
| `CellVoltage` ×3 | 4207 / 4206 / 4206 mV | **逐节电芯电压**，离散度大即失衡，可做"电芯均衡度"指示 |
| `CellCurrent` ×3 | 1146 / 1376 / 1581 mA | 逐节电芯电流 |
| `Qmax` ×3 | 6753 / 6728 / 6743 mAh | 逐节满充容量——比整机健康度更细的衰减视图 |
| `PresentDOD` | 18% | 当前放电深度 |
| `Ra00~Ra14` | 内阻表 | 电芯内阻模型参数（高级向，可做老化趋势） |

**LifetimeData —— 电池终身极值档案**（coconutBattery 级别的深度数据）：

| 字段 | 本机实测 | 含义 |
|---|---|---|
| `TotalOperatingTime` | 14510 (min) | 电池累计工作时长 |
| `MaximumChargeCurrent` | 6621 mA | 历史最大充电电流 |
| `MaximumDischargeCurrent` | (负值溢出形式) | 历史最大放电电流 |
| `MaximumPackVoltage` / `MinimumPackVoltage` | 13317 / 10726 mV | 电压极值 |
| `MaximumTemperature` / `MinimumTemperature` / `AverageTemperature` | 43.0 / 0.7 / 25.3 °C | **终身温度极值与均值** |
| `TemperatureSamples` | 232,172 | 温度采样次数 |

**其余高价值字段**：

- `RemainingCapacity` = 5232 mAh —— **当前剩余容量(mAh)**，比纯百分比更硬；
- `FullChargeCapacity` = 6225 mAh —— 实测满充容量（与 NominalChargeCapacity 6377 并存，两口径对照）；
- `DailyMinSoc` / `DailyMaxSoc` = 58 / 85 —— 今日 SoC 区间，可做"今日用电深度"；
- `TimeAtHighSoc` —— 高电量滞留时长（电池老化的核心驱动因素之一，AlDente 类产品主打的概念，这里是固件原始数据）；
- `PackReserve`、`IPDBatteryDemand`（电池侧需求功率 11910 mW）；
- 根节点 `DesignCycleCount9C` = 1000 —— **设计循环寿命**，现在只显示"124 次"，可以显示"124 / 1000"；
- 根节点 `AvgTimeToEmpty` / `AvgTimeToFull` —— 系统平滑后的时间估计，比 IOPS 瞬时值稳（65535 = 无有效值）；
- 根节点 `Voltage` / `InstantAmperage` —— 电池端电压与瞬时电流，可进明细网格。

### 2.6 IOPS 隐藏键与事件驱动

- `DesignCycleCount`（=300，与 IORegistry 的 1000 口径不同，注意甄别）、`LPM Active`、
  `Battery Provides Time Remaining`；
- `"Optimized Battery Charging Engaged"`（stats 在读，优化充电生效标志，仅在生效时出现）；
- **`IOPSNotificationCreateRunLoopSource`**：电源状态变化的 runloop 事件源，stats 用它做
  事件驱动采样。插拔电/充电状态切换可即时响应，而不是等下一秒轮询——与现有每秒帧模型
  可并存：事件触发时立即补一帧。

### 2.7 system_profiler SPPowerDataType

- **`Condition: Normal`** —— 苹果官方的电池健康状况定性结论（Normal / Service Recommended），
  比自己算百分比更权威的"该不该换电池"信号；
- 电池型号档案：Serial、Device Name、Firmware Version、Hardware Revision、Cell Revision。
- 成本高（整段 XML），按 AGENTS 红线必须走缓存（建议 60s+），适合低频刷新或展开区按需读。

## 三、第二梯队：Direct 版独占（非沙盒、无需 root）—— 本次实测重大突破

### 3.1 SMC 只读功率键实测可用

用仓库现有 `SMCReader` 同款协议写探测程序实测（非沙盒、普通用户权限）：

```
IOServiceOpen(AppleSMC): OK
PSTR   flt   19.218 W    ← 整机总负载
PDTR   flt   21.720 W    ← 适配器 DC 输入轨
B0RM   ui16  可读
B0PS   hex   可读（电池状态位）
PPBR   （stats 用作电池包功率，本次未列入探测清单，可补测）
```

- `PSTR` 与 `PowerTelemetryData.SystemLoad`（17.2W）同口径互证，
  `PDTR` 与 `SystemPowerIn` 互证——**为功率流提供了第二条独立数据链**，
  遥测停报（如维持期 BatteryPower 恒 0）时可兜底；
- stats 的电池模块即用 `PDTR`/`PPBR` + IOPS 组合，架构可参照。
- **注意**：Intel 时代的分轨功率键（`PC0C`/`PC0R`/`PM0R`/`PG0R`/`PD0R` 等
  CPU/内存/GPU/显示轨）在本 Apple Silicon 机器上**全部不存在**——
  SoC 内部组件的 SMC 分瓦数在 M 系上拿不到（见第五节）。
- 历史结论复核：`tmp/smc-sandbox-test` 旧二进制已失效（macOS 27 下崩溃/dlopen 失败），
  但"沙盒内 IOServiceOpen 被拒"的结论仍成立，故 SMC 只能进 Direct target，
  用 `#if DISPLAY_CONTROL` 同款方式隔离。

### 3.2 Direct 版可行的数据链组合

| 指标 | 主源（沙盒通用） | Direct 增强源 |
|---|---|---|
| 系统负载 | SystemLoad | SMC PSTR（交叉校验/兜底） |
| 适配器输入 | SystemPowerIn | SMC PDTR |
| 电池吞吐 | BatteryPower | SMC PPBR |

## 四、"每个软件的功耗" —— 有落地路径，且无需 root

这是你最初设想中"具体分到某个软件"的部分。**好消息：可以做到近似但可用的版本。**

### 4.1 `top -o power`：无 root 的逐进程能耗

本机实测（macOS 27，普通用户）：

```
$ top -o power -l 2 -n 6 -stats pid,command,power
PID    COMMAND          POWER
19450  Qoder CN Helper  83.8
611    WindowServer     58.3
62654  HagimiMonitor    26.6
```

- 这是与活动监视器「能耗影响」同源的相对能耗值（energy impact），按进程给出；
- **exelban/stats 的电池模块进程排行正是解析这个命令**
  （`top -o power -l 2 -n N -stats pid,command,power`，取第二段采样避免冷启动值）；
- 落地方式与项目现有 `TopCPUProcess` / `TopNetworkProcess`（nettop）模式完全一致：
  Process 拉起 → 解析 → 缓存 10s+（红线：不得每秒拉起）；
- 进程 → App 聚合：`NSRunningApplication(processIdentifier:)` 取 localizedName，
  同项目现有 Top 系列做法；
- **沙盒可行性**：项目 App Store 版已在沙盒内成功拉起 `nettop`、`system_profiler`、
  `pmset`、`ditto`，exec 系统二进制这一模式已被验证；`top` 预计同样可行，
  但 power 列依赖 top 自身对能耗数据源的访问，**需在 App Store 构建上实机确认**，
  若沙盒下该列无数据则降级为 Direct 独占功能。

### 4.2 "硬件 vs 软件"拆分能做到什么程度

- **软件侧**：`top -o power` Top N 排行 + 聚合到 App —— 可行；
- **硬件侧**：没有公开的分项硬件功率（见第五节），但可以展示**系统总功率**
  （SystemLoad）与软件排行并置，配文案"进程为估算 · 系统为实测"
  （`prototypes/power-flow/index.html` 的"耗电排行"区块已经按这个叙事设计了原型）；
- 相对值（energy impact）不是瓦特，UI 上应如实呈现为"能耗影响"而不是 W，
  或用「排行占比条」表达，避免伪造量纲（项目红线：不伪造数据）。

## 五、已确认的死路与不推荐路线

| 路线 | 结论 | 依据 |
|---|---|---|
| `powermetrics --samplers energy_model`（CPU/GPU/DRAM/ANE 分轨能量，唯一真实的硬件级拆分源） | **需要 root**，且输出含系统敏感数据，不适合产品化 | sudo 实测需密码；社区共识 |
| IOReport.framework 直连（powermetrics/活动监视器底层） | **macOS 27 本机已无此框架文件**（仅剩 IOReportFamily.kext）；历史沙盒测试 `IOServiceOpen FAILED` | 本机 dlopen 失败；`tmp/smc-sandbox-test/result.txt` |
| BatteryCenter / BatteryUIKit / PowerUI 私有框架 | dlopen 可加载（本机实测），但为私有 API，依赖 entitlement，**App Store 审核高风险**，符号随版本漂移 | 本机类枚举仅见配件电池类（BCBatteryDeviceController），主电池历史数据不在此 |
| 系统设置「电池使用情况」的 24h/10 天逐 App 耗电历史 | 存于 powerlog.db（/private/var/db），**需 root**，无公开 API | 检索确认 |
| SMC 写入（风扇/充电控制） | 已知被 thermalmonitord 拦截（kIOReturnNotPermitted），AGENTS.md 红线 | 既有结论 |
| Intel 式 SMC 分轨功率键（PC0C/PG0R 等） | Apple Silicon 上不存在 | 本次探测全部 MISSING |

**结论：SoC 内部"硬件分瓦数"（CPU 几瓦、GPU 几瓦、屏幕几瓦）对无 root 应用已无公开通路。**
系统消耗这块"分得细"的正确方向不是硬件轨拆分，而是：
整机实测总瓦数（已有）+ 固件级损耗/效率（2.1）+ 进程能耗排行（4.1）。

## 六、落地优先级建议

### P0 —— 高价值低成本，直接扩充现有数据链

1. **进程能耗排行**（`top -o power`）：补齐功率流图下方"耗电排行"区块，
   原型已存在（`prototypes/power-flow/index.html` 区块 B）；
2. **`AdapterEfficiencyLoss` 直读**：替换/校验现有差值法转换损耗；
3. **`IPDChargingAllowed`**：maintain 态改由固件直接判定，补「已达上限」与
   「优化充电暂停」的区分（配合 `NotChargingReason` 与
   `"Optimized Battery Charging Engaged"`）；
4. **`DesignCycleCount9C`**：循环次数显示为 "124 / 1000"。

### P1 —— 展开区明细网格扩充

5. 剩余容量 mAh（`RemainingCapacity`）+ 满充容量 mAh（`FullChargeCapacity`）；
6. PD 契约详情（`AdapterVoltage`/`Current`/`UsbHvcMenu`）："20V / 3.25A · 65W 档"；
7. 本次开机累计能量（`Accumulated*` 差分）：已消耗/已充入 Wh；
8. `AvgTimeToEmpty`/`AvgTimeToFull` 作为时间估计的平滑源；
9. IOPS 事件源驱动的即时补帧（插拔电立即响应）。

### P2 —— 电池深度档案（可做成独立展开页）

10. 终身极值档案（LifetimeData：温度/电流/电压极值、累计工作时长）；
11. 电芯均衡视图（逐节 CellVoltage / Qmax）；
12. 今日 SoC 区间（DailyMin/MaxSoc）与高电量滞留（TimeAtHighSoc）；
13. 官方健康定性（system_profiler `Condition`）。

### Direct 版附加

14. SMC `PSTR`/`PDTR` 第二数据链（`#if DISPLAY_CONTROL` 隔离），
    遥测停报期兜底 + 双源交叉校验。
