# 数据统计功能需求分析与设计报告

> 版本：V1 · 2026-08-22
> 状态：已实现 V1，待目测验收
> 关联：项目早期曾规划过「统计报表」后搁置；本报告按当前监测指标全量重新设计，不复用旧方案。

---

## 1. 背景与目标

HagimiMonitor 目前面板与菜单栏只呈现**瞬时值**（1~10s 节奏采样的最新一帧），
历史信息仅存于内存中 24 点的 sparkline。用户无法回答这类问题：

- 「今天电脑平均负载多少？什么时候最忙？」
- 「这个月下载了多少流量？白天还是夜里用得多？」
- 「最近一周内存是不是越来越吃紧？」
- 「电池花在充电/放电/直供上的时间比例如何？」

本功能引入**本地历史统计**：持续记录全部监测指标 → 聚合存储 → 以
「设置内简要总览 + 可跳转的自包含 HTML 深度报表」两个层次呈现。

### 设计原则

1. **绝不伪造数据**：与采样器纪律一致——没有记录的时段留空（图上为空隙），
   不补 0、不插值伪装成真实采样。报表是诚实的快照。
2. **全部数据留在本机**：SQLite 落在应用支持目录，报表 HTML 由 App 本地生成，
   无任何网络上报。
3. **两渠道同构**：App Store 沙盒版与 GitHub 直连版共用一套统计层；
   Direct 独有数据源（CPU 温度、风扇）按可用性条件呈现，文案不出现渠道术语。
4. **零打扰**：统计写入走后台串行队列，主线程只做内存累加；
   面板动画/采样节奏不受影响。

## 2. 需求分析

### 2.1 统计范围（指标盘点）

以「设备与软件里能看到的信息」为边界盘点，V1 全量纳入**数值型时序指标**
（可求均值/峰值/累计）；静态信息（IP 地址、SSID、型号、SMART 状态）与
列表型信息（TOP 进程、蓝牙设备清单）不进历史库：

| 模块 | 记录指标 | 口径 | 渠道 |
|---|---|---|---|
| CPU | 总占用、system/user、P 核均值、E 核均值 | %，均值+峰值 | 双渠道 |
| CPU | 热压力（thermalState 0-3） | 档位均值 | 双渠道 |
| CPU | 温度 | °C 均值 | 仅 Direct（SMC） |
| GPU | 占用率、tiler 占用 | %，均值+峰值 | 双渠道 |
| GPU | 显存占用 | 字节均值 | 双渠道 |
| 内存 | 占用率（%）、已用/压缩/交换字节、压力百分比 | 均值+峰值 | 双渠道 |
| 网络 | 上/下行速率 | 均值/峰值速率 + 分钟累计字节 | 双渠道 |
| 磁盘 | 读/写速率 | 均值/峰值速率 + 分钟累计字节 | 双渠道 |
| 电池 | 电量、系统功率、电池温度 | 均值（+功率峰值） | 双渠道 |
| 电源 | 插电时间占比、充电时间占比 | 分钟内采样占比 | 双渠道 |
| 风扇 | 最大转速 | 均值+峰值 | 仅 Direct（SMC） |

桌面机型（无电池）电源侧恒为「直供」，报表自动隐藏电池专属区块——
区块级降级而非渲染空图。

### 2.2 时间维度

- **预设范围**：今日 / 近 7 天 / 近 30 天 / 今年 / 全部；
- **自定义**：起止日期选择器，任意区间；
- **粒度自适应**：≤2 天用分钟粒度，≤60 天用小时粒度，更长用日粒度。
  粒度切换对用户透明，只感知「范围」。

### 2.3 双展示面差异化

| | 设置页「数据统计」模块 | HTML 深度报表 |
|---|---|---|
| 定位 | 路过看一眼的仪表小卡 | 正襟危坐的分析工作台 |
| 范围 | 固定「今日 + 近 7 日」 | 全部范围 + 自定义区间 |
| 呈现 | 数字卡 + 单条迷你柱状 | 11 类图表 + 汇总表 + 洞察 |
| 打开方式 | 设置侧栏 | 设置页按钮 / App 菜单「打开数据报表」 |

设置页要**给理由**（今天有数、一眼有货），网页端要**给回报**
（宏观、可对比、能回答「这段时间电脑过得怎么样」）。

## 3. 总体架构

```
SystemMonitorSampler ─┐
FanSampler ───────────┤   每秒一帧（主线程发布）
BluetoothBatterySampler ┘          │
                        MonitorStore.applySamplingSuccess()
                                   │  （主线程，纯内存累加，微秒级）
                        StatisticsRecorder.record()
                                   │  分钟封口 → 后台串行队列
                        StatisticsDatabase（SQLite3，系统库零依赖）
                        ├ stats_minute（分钟行，保留 45 天）
                        ├ stats_hour （小时行，保留 400 天）
                        └ stats_day  （日行，永久）
                                   │
              ┌────────────────────┴────────────────────┐
     StatisticsSettingsView（今日/近7日概览）   StatisticsReportBuilder
                                              （模板 + 数据注入 → 单文件 HTML → 浏览器）
```

### 聚合口径

- **分钟行**：对该分钟内到达的每秒帧，按指标独立累加（各指标采样节奏 1~10s 不一，
  互不等待）；均值 = Σx/n，峰值 = max；
- **速率型指标**（网络/磁盘）：以「速率 × 距上次观测时长」逐段积分得分钟字节数，
  间隔上限 30s——超过视为睡眠/间隙，该段丢弃，不虚增总量；
- **占比型指标**（插电/充电）：分钟内出现次数占比 0~1；
- **小时/日行**：由分钟行按本地时区对齐汇总（均值按采样数加权，总量求和，
  峰值取最大，占比加权）；
- **空隙语义**：机器睡眠期间无帧 → 无分钟行 → 图表显示断点。这是真实的使用记录。

### 保留策略

启动时与每日翻日时执行：分钟 > 45 天清除、小时 > 400 天清除（先完成增量汇总）。
单行约 30 列，一年小时行 8760 行、日行 365 行，库体积年增 < 2MB。

## 4. 设置页「数据统计」模块设计

侧栏新增独立分区入口（chart.bar.doc.horizontal 图标，位于模块组与关于之间）：

```
┌──────────────────────────────────────────────┐
│ [图标] 数据统计   已记录 N 天 · 占用 X MB      │
│                          [ 打开数据报表 ]      │
├──────────────────────────────────────────────┤
│ 数据总览        [今日 | 近 7 日 | 近 30 日]     │

│ └────────┘ └────────┘ └───────┘   标注+等宽值) │
│ ┌网络────┐ ┌磁盘────┐ ┌电源────┐              │
│ │↓下行 130M│ │读 48.1 GB│ │插电 100%│             │
│ │↑上行 128M│ │写 12.9 GB│ │功率 2.8 W│            │
│ └────────┘ └────────┘ └───────┘              │
├──────────────────────────────────────────────┤
│ 完整报表                                      │
│ 在浏览器中打开可交互的多维报表（含热力图、       │

└──────────────────────────────────────────────┘
```

- **范围切换**：今日 / 近 7 日 / 近 30 日三档，整组总览卡随切换刷新——
  总览回答「这段时间机器过得怎么样」，而不是只看单指标；
- 一格一义：每个数值都有明确标注（均值/峰值/下行/上行/读/写/插电/功率），
  等宽数字统一字号，不混排大小字；
- 尚无数据（刚安装）时显示「数据从现在开始积累」空态卡；
- 「打开数据报表」按钮与 App 菜单入口共用同一条生成-打开链路。

## 5. 网页报表设计（核心交付）

### 5.1 形态与视觉

- **单文件 HTML**：ECharts 与图标全部内嵌，数据以 `window.__DATA__` 注入，
  双击即开、离线可用、可归档/分享，不依赖任何 CDN；
- **视觉语言**：与 App 一致的深色玻璃拟态——近黑蓝底、卡片 16px 圆角、
  半透明分层、模块主色沿用 App 调色板（CPU 橙 / GPU 紫 / 内存青 / 网络青绿 /
  电池绿 / 磁盘卡其）；
- **图标**：Lucide 线性图标（内嵌 SVG），UI 全程无 emoji；
- **三语**：报表按 App 当前语言生成（中/英/日）。

### 5.2 信息架构（自上而下）

1. **报告头**：设备名/机型、系统版本、数据覆盖天数、生成时间、
   范围切换器（今日/7 天/30 天/今年/全部/自定义起止）；
2. **KPI 概览条**：CPU 均值/峰值、GPU 均值/峰值、内存均值/峰值、
   网络下/上行总量、磁盘读/写总量、电源构成；
3. **负载总览**：CPU/GPU/内存压力三线面积图（0-100%，同一时间轴可比）；
4. **活动热力图**：GitHub 贡献图式「星期 × 小时」繁忙度矩阵——
  一眼看出这台机器的工作节律（综合负载 = max(CPU, GPU, 内存压力) 的小时均值）；
5. **CPU 区**：均值/峰值包络面积图；P/E 核堆叠面积（有拓扑时）；
  使用强度分布环图（<10 / 10-30 / 30-60 / 60-90 / 90+% 时间占比）；
6. **GPU 区**：占用率曲线 + 强度分布环图 + 显存占用面积；
7. **内存区**：构成堆叠面积（压缩/其他已用）+ 交换使用曲线 + 压力百分比；
8. **网络区**：下/上行速率曲线（对数感知分轴）+ 每日流量柱状（双向）；
9. **磁盘区**：读/写速率曲线 + 每日读写字节柱状；
10. **电源区**（有电池数据时）：电源构成环图（直供/充电/电池）+ 电量曲线 +
    系统功率曲线；无电池机型显示「直供占比 100%」简化卡；
11. **温度与风扇区**（数据存在时）：CPU 温度（Direct）、电池温度、风扇转速曲线；
12. **每日汇总表**：日期 / CPU 均值/峰值 / 内存均值 / 网络下行/上行 / 磁盘读写 / 电源构成 / 覆盖时长；
13. **洞察卡**（自动推导）：最忙时段、平均负载评价、峰值事件（何时 CPU 最高）、
    数据覆盖率提示；
14. **页脚**：生成方式与只读快照声明、数据覆盖说明。

图表选型理由：时序看**趋势**用面积/折线；构成看**占比**用环图；
节律看**规律**用热力图；累计看**体量**用柱状——四类问题各配最短认知路径的图形。

### 5.3 交互

- 范围切换即时重绘（纯前端，数据已全量内嵌）；
- 自定义范围：两个日期输入 + 应用；
- 所有折线开启 tooltip 联动与 dataZoom 缩放（大范围下拖拽看局部）；
- 空数据区块折叠为「该范围无记录」占位，不渲染空坐标系。

## 6. 技术方案要点

| 决策 | 选择 | 理由 |
|---|---|---|
| 存储 | 系统 SQLite3（C API 直连） | 零第三方依赖；沙盒可用；查询聚合成熟 |
| 落库线程 | 独立串行 DispatchQueue | 主线程零 IO；写锁自然串行 |
| 图表库 | ECharts 5（内嵌 echarts.min.js） | 热力图/环图/dataZoom 全齐，深色主题易定制，中文生态 |
| 图标库 | Lucide（内嵌 SVG symbol） | 现代线性风格，与 SF Symbols 气质连续 |
| 报表生成 | Bundle 内模板 + `__DATA__` 注入 + 资源内联 | 单文件、离线、无 CDN 方差 |
| 文件位置 | `~/Library/Application Support/<bundleID>/` | 双渠道 Bundle ID 不同，天然隔离 |
| 测试 | 聚合口径单测（Recorder 累加/积分/封口、DB 汇总/保留期） | 采样节奏不进测试，纯函数化 |

## 7. V1 边界与后续迭代

- 报表导出 PDF/CSV、打印样式；
- 设置页概览的时间范围切换 ~~（固定今日+7 日）~~ → 已实现（今日/近 7 日/近 30 日三档）；
- 菜单栏面板内嵌迷你报表。

### 7.1 旧版统计功能考古与回植（2026-08-22 第三轮）

用户指出项目早期存在一版被删除的统计功能（删除提交 `6cddfdfa`，旧实现约 4900 行：
SwiftData 存储、健康评分、事件系统、1390 行 HTML 导出器）。考古后按价值回植：

**已回植**：

1. **健康评分**：完整沿用旧版维度健康度模型——CPU 曲线（70% 前宽容）、GPU 线性、
   内存压力按 /50 折算等级、热状态 0-3 档曲线；缺失维度权重再分配；
   平均热状态 ≥ serious 时评分硬帽 40 并明示；五级评级与等级色。
   双端实现：Swift `StatisticsHealthScore`（设置页评分环+维度徽章，随范围切换）、
   报表 JS 同口径（评分卡 + 逐桶评分走势线）。磁盘维度未纳入（统计层不录剩余空间），
   权重相应重归一化（CPU .41 / GPU .24 / 压力 .29 / 热 .06）。
2. **事件时间线**：改为**从统计数据即时推导**（旧版是独立事件表落库）——
   CPU 持续高载（连续桶均值 ≥90）、内存压力偏高（≥60）、热压力升高（≥serious）、
   网络/磁盘尖峰（> 范围中位数 8 倍且 >100MB）、电源切换（ac 占比跨 0.5）。
   优点：零额外存储、任意历史范围可回溯。按严重度优先排序，上限 30 条。
3. **明暗双主题**：旧版报表跟随系统外观的样式思路回植——CSS 变量双套 +
   ECharts 调色板随 `prefers-color-scheme` 切换并全量重绘。
4. 顺带修复：报表生成时间戳秒/毫秒口径自适应（曾显示 1970）。

**考古后不回植**（记录理由）：旧版每模块直方图（现有强度环图已覆盖该认知路径，
直方图更细但信息冗余）；持久化事件表（被即时推导取代）；设置页内事件时间线
（设置页保持轻量，分析交给网页端）；评分维度提示 Popover（维度徽章已带原始值）。

### 7.2.1 V3 增量：存储管理与双展示面视觉升级（2026-08-22 第五轮）

**触发**：代码评审 + 用户验收反馈——缺存储管理（无法查看/清理本地数据、不知占用）；
设置页过于朴素、核心数据不突出；报表展示欠人性化、缺现代设计感。

**存储管理（新）**：

- 设置页新增「存储管理」组：占用卡（统计库/应用统计/报表文件三段比例条 + 各自字节数 +
  总占用 + 记录条数）、历史数据浏览（日/周/月三档：CPU 均值迷你柱图 + 逐桶明细表
  日期/CPU/内存/网络↓↑/磁盘读写/覆盖时长）、清理（删除 30/90/180/365 天前数据、
  清空全部，均带确认对话框，删除后占用与总览即时刷新）。
- 数据层 API：`StatisticsDatabase.rowCounts/deleteBefore/deleteAll`（删除后 VACUUM
  收缩文件使占用立即回落）；`StatisticsProcessStore.fileSize/deleteBefore(day:)/deleteAll()`
  （打卡行删除后按剩余活跃日重校 `StatsUsageMeta`，应用身份保留——历史行名称/图标来源）；
  `StatisticsRecorder.storageInfo`（随概览发布的三类占用+三层行数快照）、
  `storageBuckets(_:completion:)`（日桶 = 日层 + 今日分钟现算；周/月按本地时区归组）、
  `deleteData(before:)/deleteAllData()`（后台执行、主线程回调、完成后 refreshOverview）。
- 顺带修复：`lastBatterySlow` 原在主线程写、后台队列读（数据竞态），改为封口时主线程
  捕获随闭包带入后台。

**设置页重设计**：头部图标改渐变徽章；健康评分卡升级（76pt 渐变描边评分环 + 等级胶囊 +
维度徽章带原始值）；总览六格改「模块色图标芯片 + 同色浅底圆角 tile」形态（配色与报表
模块主色同套、双主题各一档）；存储管理组见上。

**报表现代化**：标题渐变文字；粘性分区导航（从实际渲染分区收集锚点、滚动高亮、隐藏分区
不入导航）；分区标题图标芯片化（同色浅底）；KPI/洞察图标芯片化 + KPI 数字 650ms 缓动
滚动；面积图全部改垂直渐变填充（含 P/E 堆叠与内存构成）；应用排行进度条渐变；卡片悬浮
微交互；分区滚动进场（IntersectionObserver，`prefers-reduced-motion` 全降级）；
回到顶部悬浮按钮。全部增强包在独立 try/catch，失败不拖垮数据区。

**报表 bug 修复**：① 打卡提示文案（`checkinHint`）原先赋值给未挂载节点，现正确显示；
② 「今日」范围下洞察「最忙时段」误用全量 60 天小时数据，现裁剪到所选窗口。

**验证**：双 scheme 构建通过；swiftc harness 10 项断言覆盖 deleteBefore/deleteAll/rowCounts/

### 7.2.3 健康评分 V2：应力模型重构（2026-08-22 第七轮）

**触发**：用户评估旧公式后认同「忙=不健康」缺陷；外部审查七点意见定稿。

**哲学**：高负载不扣分，只罚不健康状态。分数语义=「健康时间占比」。
电池健康度**不纳入**（硬件属性而非窗口状态），由报表电池区/洞察单独呈现；
电池温度可进热应力回退。

**数据层（审查 #1）**：非线性曲线只作用在帧级。`StatisticsRecorder.record()` 每帧算
四个子应力存新列 `stress_mem_avg/stress_thermal_avg/stress_cpu_avg/stress_gpu_avg`
（追加列尾，旧库 ALTER 迁移 NULL）；评分/报表只做线性重组，Jensen 偏差根除。

**曲线定稿**（帧级，Swift `StatisticsHealthScore` 与报表 JS 同口径）：

- s_cpu：≤85 不罚，85~100 线性→1；s_gpu：≤90 不罚，90~100→1；
- s_mem（审查 #2）：内核裁定 `pressure-level` 为主（warning 0.6/critical 1.0），
  连续水位 60% 起点缓变塑形至多 0.55——「忙但无压力」零扣分；
- swap **整体移出评分**（审查 #3：惩罚历史、不随硬件缩放；level 裁定已覆盖真压力）；
- s_thermal（审查 #4）：thermal 档位 0/1/2/3→0/0.2/0.6/1.0；温度**仅**档位缺失时
  回退（沙盒），85°C 起罚，不作并行放大器。

**合成**：stress=0.45·m+0.30·t+0.15·c+0.10·g；score=100×(1−stress)。
缺维度不扣分**不归一**。软帽（审查 #5）：窗口 stress_thermal 均值≥0.01
（≈1% critical/2% serious 时长）评级至多「良好」。阈值收紧（审查 #6）95/85/70/50。

**双端 parity（审查 #7 降级落地）**：非线性归帧级后共享面缩成线性重组；
验证=swiftc harness 五组断言（空闲 100/忙而健康 94/不健康 42.6/软帽 97→良好/
旧行回退 90）+ 同 payload 浏览器渲染对照（周窗口双端同 100）。
永久 JSC parity 测试待 `xcodebuild test` 环境恢复后补。

**展示**：维度徽章改应力时长占比（CPU 饱和/GPU 饱和/内存压力/过热 + %），
等级色按占比分档；热帽文案改「过热时长占比超阈值,评级至多良好」。三语同步。

### A.3 存储一：统计 SQLite（`StatisticsDatabase.swift`）

- **位置**：`~/Library/Application Support/<bundleID>/statistics.sqlite3`（WAL 模式；
  沙盒版在容器内，两渠道天然隔离）。
- **三张表** `stats_minute` / `stats_hour` / `stats_day`，同构：`t INTEGER PK`（桶起点，
  分=分钟起点，时=本地小时起点，日=本地日起点）+ 35 个 REAL 列 + `n INTEGER`（帧数）。
- **35 列**（`StatisticsRow.columns` 单一来源，顺序即 SQL 列序/报表 JSON 列序）：
  `cpu_avg,cpu_max,cpu_sys_avg,cpu_user_avg,cpu_p_avg,cpu_e_avg,cpu_thermal_avg,cpu_temp_avg,
  gpu_avg,gpu_max,gpu_tiler_avg,gpu_mem_avg,mem_pct_avg,mem_pct_max,mem_used_avg,mem_comp_avg,
  mem_swap_avg,mem_pressure_avg,net_down,net_up,net_down_peak,net_up_peak,disk_read,disk_write,
  disk_read_peak,disk_write_peak,batt_level_avg,ac_frac,charging_frac,batt_temp_avg,power_avg,
  power_max,fan_avg,fan_max,uptime_avg`
- **聚合规则**（列名后缀驱动，`StatisticsAggregation`）：`_avg/_frac` = 按 n 加权平均；
  `_max/_peak` = 取最大；无后缀（net/disk 总量）= 求和。上卷（分→时→日）同规则。
- **保留期**：分钟 45 天、小时 400 天、日永久；先汇总后清理。
- **迁移**：建表后逐列 `PRAGMA table_info` 比对，缺列 `ALTER TABLE ADD COLUMN`（uptime_avg
  即靠此机制进入旧库）。**新增列务必追加在 columns 末尾**，否则 JSON 列序错位。
- **线程模型**：所有公开方法内部 `queue.sync`，任意线程可调；写入只在分钟封口/maintain。

### A.4 存储二：SwiftData AppStats（`StatisticsProcessStore.swift`）

- **位置**：`~/Library/Application Support/<bundleID>/AppStats.sqlite`，独立 ModelContainer，
  专用串行队列 + 队列上创建的 `ModelContext`（注意：**新 SDK 无 `makeModelContext`**，
  用 `ModelContext(container)` 初始化；`autosaveEnabled = false` 手动 save）。
- **实体**：
  - `StatsAppIdentity`：`appKey`(=应用显示名,unique) / `name` / `iconPNG`(64px PNG Data)。
    **图标只在首见时转码落库一次**——应用卸载后历史报表仍显示名称与图标。
  - `StatsAppDaily`：`day`(yyyymmdd Int64) + `appKey` + cpuScore/cpuSamples（均值=商）、
    gpuScore/gpuSamples、memSum/memSamples、netDown/netUp/diskRead/diskWrite（字节总量）。
    fetch-then-update upsert，无外键关系（按 appKey 关联）。
  - `StatsBatteryDaily`：day + cycleCount + healthPercent（同日后到者为准）。
  - `StatsActiveDay`：day unique——当天有过任何采样即插入（打卡点亮依据）。
  - `StatsUsageMeta`：firstUseDay / totalActiveDays / lastActiveDay。
- **降噪阈值**（record 入账门槛）：CPU/GPU ≥0.5%、内存 ≥64MB、网络 ≥5MB、磁盘 ≥10MB。
- **API 值类型进出**（`DailyAppRow`/`AppRankEntry`/`BatteryPoint`/`UsageSummary`），调用方不接触托管对象。

### A.5 采集挂接（`MonitorModels.swift`）

1. `MonitorStore` 持有 `let statisticsRecorder = StatisticsRecorder()`；
   `applySamplingSuccess()` 末尾调用 `statisticsRecorder.record(modules: allModules, fans: fans, at: Date())`——
   读 `allModules`（非 visible modules），**用户在设置里隐藏的模块照常进统计**。
2. `startStatisticsProcessSampling()`：60s Timer（init 启动、deinit 取消），调
   `sampleProcessesForStatistics()`——procSampleQueue 采 CPU/内存/GPU（+Direct 磁盘）、
   nettopQueue 采网络（仅 Direct）；`limit: 12, includeSystemProcesses: true`；
   enrich 后回主线程 `recorder.recordProcesses(...)`（类型化 struct 参数）。
   **必须走这两条既有队列**：进程差分快照是文件级全局状态，串行是正确性前提。
   网络速率（nettop 窗口均值）×60s 折算分钟字节量。
3. 电池慢变量（cycle-count/health）在 `accumulateBattery` 缓存，分钟封口时按日落库。

### A.6 报表生成管线（`StatisticsReportBuilder.swift` + `Resources/ReportTemplate.html`）

- 模板含三个占位符：SVG 图标 sprite（构建期已内联 Lucide 19 枚）、`/*__ECHARTS__*/`

### A.8 健康评分口径（Swift `StatisticsHealthScore` 与模板 JS 同公式）

- 维度与权重（磁盘未纳入——统计层不录剩余空间；权重为剔除后重归一化）：

- 曲线：CPU 宽容至 70%（70→0.85, 90→0.30, 100→0）；GPU 线性；内存压力% ÷50 折算等级后

- 五级：excellent≥85 / good≥70 / fair≥50 / poor≥30 / critical，等级色双主题各一套。

### A.9 事件时间线（即时推导，无独立事件表）

从当前范围 rows 扫描推导（优于旧版落库方案：零存储、任意历史范围可回溯）：
- CPU 持续高载：连续桶 cpu_avg≥90（≥3 桶），均值≥95 升 critical；

### A.13 实测坑清单（接手必读）

1. **动态 i18n 键**：见 A.6——报表文案只能走 `Bundle.localizedString`。
2. **DispatchQueue 尾随闭包**：多语句（含 `#if`）尾随闭包直接 `queue.async {}` 会被误判
   DispatchWorkItem 报错——先 `let work: () -> Void = {...}` 再 `queue.async(execute: work)`；
   跨对象传参用类型化 struct，勿用元组数组。
3. **SwiftData**：新 SDK 无 `makeModelContext`，用 `ModelContext(container)`；
   ModelContext 非线程安全——专用串行队列上创建并只在该队列使用。
4. **模板 JS**：const 声明顺序（TDZ）曾让整页渲染链中断，新增代码注意声明先于使用；
   分区渲染务必保持 try/catch 隔离。
5. **列序契约**：`StatisticsRow.columns` 顺序 = SQL 列序 = 报表 JSON 列序 = JS `IDX` 映射，
   新列只能追加末尾。
6. **进程采样队列红线**（承 AGENTS.md）：差分快照只被 procSampleQueue/nettopQueue 串行读写，
   统计采样必须复用这两条队列，不得另开并发路径。
7. **`generatedAt` 秒/毫秒**：JS 端已做 `<1e12 ? ×1000` 自适应，新代码统一发秒。
8. **ALTER 迁移列排在 n 之后，`SELECT *` 位置假设必错**：表物理序为
   `t, 数值列…, n`，`ALTER TABLE ADD COLUMN` 把新列追加到 n **后面**；按
   「列序契约」位置读会把 n 读成新列（应力列上线时真实库读出 n=0，评分与
   均值全灭）。`fetchRows` 必须显式列名取数（`SELECT t, <columns…>, n`）。
   故障窗口内被 n=0 污染的时/日桶，修复后 rollup 重扫最后一桶自动自愈。
