# 面板展开动画性能分析报告

- **日期**：2026-08-21
- **分支**：`feature/expansion-anim-swiftui-native`（对照：`dev`）
- **环境**：Apple Silicon（ARM64），macOS 27.0 (26A5416b)，Debug 构建，`HagimiMonitorDirect` scheme
- **方法**：新增 `AutotestPerfMeter`（主线程/进程 CPU 时间 + 掉帧计数），用 `HAGIMI_PANEL_AUTOTEST="1.2:13"` 自动开关面板 13 次、每次可见后全量展开，取 7 个有效样本均值；辅以 `/usr/bin/sample` 抓主线程调用栈。

---

## 一、背景：两版架构

| | `dev` | `feature/expansion-anim-swiftui-native` |
|---|---|---|
| 内容高度 | `PanelExpansionDriver` 在主 RunLoop 以 **60Hz Timer** 逐帧发布 `phase[@Published]`，`CollapsibleDetail` 读相位设 `.frame(height:)` | `withAnimation(.easeInOut(0.15))` 驱动 `isExpanded`，`.animation(value: isExpanded)` 插值高度 |
| 窗口 frame | 内容逐帧变高 → GeometryReader 上报 → `setPanelFrame` 被动贴合 | toggle 时一次性把预测终高交给 `panel.animator().setFrame`，CA 补间；`isAnimatingExpansion` 抑制期间逐帧回调 |
| 主观感受 | 卡 | 顺一些，但 CPU 仍高 |

两版都受同一个结构性约束：菜单栏面板要求窗口尺寸贴合内容，而展开要求内容高度在 ~0.15s 内连续变化。

---

## 二、基线数据（feature 分支，现状）

每次展开的度量窗口为 `panelExpansionDuration(0.15) + 0.08s settle` ≈ 0.23s。

| 场景 | 主线程 CPU | 进程 CPU | slowframes (>8.3ms) |
|---|---|---|---|
| **全量展开（autotest 默认）** | **209–221 ms** | 233–247 ms | ~10 |
| **单行展开（`HAGIMI_AUTOTEST_SINGLE=1`）** | **183 ms** | 192 ms | ~10 |

要点：

- 主线程占用 ≈ 210/235 ≈ **90%**，0.23s 窗口里约 14 帧有 10 帧掉帧。
- `proc − main` ≈ 30ms，后台采样队列贡献很小（`beginExpansionAnimation()` 已推迟主采样）。
- **单行 ≈ 全量**：每帧开销是**固定成本**，与展开多少内容无关。这是关键线索——说明贵的不是"展开了多少明细"，而是"每帧做一次高度动画 + 窗口 resize"本身。

---

## 三、归因实验（6 组 A/B，运行时环境变量开关）

为定位瓶颈，加了 `PanelPerfHooks`（默认全关、生产零开销），逐组开关单个可疑因素：

| 实验（开关） | 主线程 CPU | slowframes | 结论 |
|---|---|---|---|
| **baseline** | 209 ms | 10.3 | — |
| 冻结全部毛玻璃（`HAGIMI_FREEZE_GLASS=1`）：动画期把窗口 `.behindWindow` + 每行 `.withinWindow` 的 `NSVisualEffectView.state` 置 `.inactive` | 217 ms | 10.4 | ❌ 无效，反略升 |
| 短路每帧 ScrollView 几何回调（`HAGIMI_SKIP_CALLBACKS=1`） | 214 ms | 10.9 | ❌ 无效 |
| 关电池流光 TimelineView（`HAGIMI_NO_FLOW_TIMELINE=1`） | 209 ms | 10.6 | ❌ 无效（主要吃 GPU） |
| 只窗口动画、内容瞬时布局（`HAGIMI_CONTENT_NOANIM=1`） | **146 ms** | 8.4 | ✅ **省 ~63ms（30%）** |
| 窗口 + 内容都瞬时（地板值） | 125 ms | 5.6 | 一次性挂载成本 ≈125ms |
| 内层固定全高 + 外层裁剪（`HAGIMI_FIXED_INNER=1`） | 192 ms（单行） | 9.6 | ❌ 无效，逐帧成本不在明细子树重布局 |
| 窗口瞬时、只内容动画（`HAGIMI_INSTANT_WINDOW=1`） | 220 ms | 10.7 | ❌ 无效，窗口 CA resize 本身不贵 |

### 结论

1. **瓶颈是 SwiftUI 内容高度的逐帧动画**，不是窗口 CA resize，不是毛玻璃，不是流光，不是每帧几何回调。
2. 去掉内容逐帧动画、只留窗口动画，立刻省 **~63ms / 30%**。
3. 剩下 ~125–146ms 是"半透明 + 10 个毛玻璃子层的窗口逐帧 resize"的结构性地板 + 首次挂载明细的一次性布局/CA 提交。
4. 毛玻璃/流光主要消耗在 GPU / WindowServer，不在主线程；冻结它们对主线程 CPU 无帮助（活动监视器里 WindowServer 峰值 ~48%，但主线程瓶颈在 app 自身）。

## 四、`sample` 主线程热点

8 秒采样覆盖约 6 次展开，各框架出现频次：

| 框架 | 采样命中 |
|---|---|
| AppKit | 1422 |
| QuartzCore | 725 |
| SwiftUI | 643 |
| AttributeGraph | 575 |
| 自有代码（HagimiMonitor.debug.dylib） | 500（多被内联） |

命中的关键系统路径：

- `CA::Render::Context::wait_for_synchronize`（QuartzCore）——主线程每帧在等渲染服务同步；
- `ViewRendererHost.updateViewGraph` / `ViewLayoutEngine.sizeThatFits`（SwiftUICore）——每帧 SwiftUI 布局事务；
- `StackLayout.placeChildren` / `LayoutEngineBox.explicitAlignment`（SwiftUICore）——VStack/ScrollView 逐帧布局；
- `-[NSISEngine withBehaviors:performModifications:]`（CoreAutoLayout）——hostingView 四边约束随窗口 resize 求解；
- 自有代码仅在 `MonitorPanelView.body.getter` 等薄层命中，无重量级自有函数。

这印证：每帧成本是 SwiftUI 布局事务 + CA 图层提交 + AutoLayout 求解的**框架固定开销**，与展开内容量无关。

---

## 五、确定的优化方案：窗口驱动揭示

实验中"只窗口动画、内容瞬时布局"（146ms）验证了方向。把它落成正式架构：

- **内容瞬时布局到终高**：`CollapsibleDetail` 的 `.frame(height:)` 不再逐帧插值（`.animation(nil, value: isExpanded)`），toggle 时一次布局完成；
- **窗口 CA 动画揭示**：窗口 frame 从收起高度用 `animator().setFrame` 动画到终高，`NSVisualEffectView` 的 `masksToBounds` + hosting 顶部对齐（`.frame(maxHeight:.infinity, alignment: .top)`）让内容随窗口下沿生长被逐步裁出；
- **chevron 旋转等次级动效**仍由 `withAnimation` 驱动（GPU 变换，不触发布局）。

这正是系统 `NSPopover` 的做法，且**从根上消除"两层错位"**：只有窗口一个东西在动，不存在内容与边框不同步。

预期：主线程 CPU 从 ~209ms 降到 ~146ms（−30%），slowframes 从 10 降到 ~8；视觉从"内容卷出"变为"窗口生长揭示"。剩余 ~146ms 是该交互模式的结构性地板（半透明窗口逐帧 resize），进一步优化需牺牲毛玻璃或改非动画呈现，性价比低。

## 五之二、窗口驱动方案的实测试用反馈与回退（2026-08-21 当日第二阶段）

「窗口驱动揭示」实装后用户目测反馈两个问题：

1. **展开/收起观感不一致**：展开时内容瞬时到位、只有窗口下沿生长，行的位移是瞬移，「动画基本消失」；收起时（为防空玻璃用了延迟卸载）底部行被上升的窗口下沿逐个裁掉、结尾行再瞬移，观感「缓缓收回、突兀」。行要滑动就必须让 SwiftUI 逐帧插值高度（那 63ms），要省 CPU 行就只能瞬移--结构性取舍。
2. **双击 header 收起偶发整页消失**（真 bug，见下）。

**决策**：用户在「双向平滑（~210ms）/ 展开快+收起平滑 / 双向瞬时（~147ms）」中选择了**双向都平滑滑动**--恢复提交版的 `withAnimation` 内容高度动画，观感一致优先，接受 0.15s 的 CPU 峰值。

### 双击收起「整页消失」的根因链（提交版即存在）

1. **基线校准中毒**（`PanelExpansionDriver.recalibrateBaseHeight`）：驱动器用 `实测高度 − Σ(相位×自然高度)` 反推收起基线。当全部展开的内容**超过屏幕可用高度**时 ScrollView 封顶，实测被钳住（如内容 900pt、实测 700pt），等式失真，基线被解出 700−600=100（真实收起高度 300，极端时为负）。此后 `predicted = 中毒基线` 把窗口 CA 到近乎 0 高度 → 整页消失。
2. **上报丢弃无重试 + 复位竞态**：内容稳定后的尺寸上报若落在 `isAnimatingExpansion` 为 true 的窗口内会被丢弃且永不重试；标志复位（t+0.17s）与上报（t+δ+0.17s）毫秒级赛跑，输了窗口就**永久卡死**在错误高度。快速连续 toggle 时早先动画的复位定时器还会提前放行逐帧贴合，进一步扩大竞态。

### 修复（与动画方向无关，双向平滑版同样受益）

- **驱动器封顶感知**：视图上报 `effectiveContentHeightCap`；实测高度触及上限时**跳过基线校准**（保留上次一致值），预测值钳制在上限内且不为负（`PanelExpansionDriver.swift`）。
- **复位 token 化**：`applyWindowHeight` 每次递增代号，只有最新一次动画的复位回调能清 `isAnimatingExpansion`；早先的复位定时器自然失效（两个 controller）。
- **动画结束对账**：复位时若窗口尺寸 ≠ 最近上报的内容尺寸，补贴合一次--「卡死在错误高度」这一类问题被整体封死。
- **高度下限兜底**：预测值经 `max(·, 96)` 钳制，任何上游异常都不会把窗口带到不可见高度。

### 回归数据（修复后，双向平滑动画）

- autotest 13 轮：收起 418.5pt ↔ 全展 935.0pt 每轮稳定往返，无异常高度、无卡死；`main ≈ 214ms`（与提交版同级，符合选型预期）。

## 六、度量工具

### `AutotestPerfMeter`（新增，保留）

`HagimiMonitor/Views/Panel/AutotestPerfMeter.swift`，`HAGIMI_PANEL_AUTOTEST` 门控，生产零开销。每次展开输出：

```
[autotest] expand main=206.9ms proc=246.6ms slowframes=10 wall=235.5ms
```

- `main`：Mach `thread_info(THREAD_BASIC_INFO)` 取主线程 user+system CPU；
- `proc`：`getrusage(RUSAGE_SELF)`；
- `slowframes`：现有 4ms 主线程打卡探针在度量窗口内 >8.3ms 的次数；
- `wall`：`CACurrentMediaTime()` 墙钟。

### 运行方式

```bash
# 构建
xcodebuild -project hagimi-monitor.xcodeproj -scheme HagimiMonitorDirect -configuration Debug \
  CONFIGURATION_BUILD_DIR=/tmp/hagimi-build \
  -derivedDataPath /tmp/hagimi-build/DerivedData build
# 跑 13 次自动展开
HAGIMI_PANEL_AUTOTEST="1.2:13" /tmp/hagimi-build/HagimiMonitor.app/Contents/MacOS/HagimiMonitor 2>&1 \
  | grep '\[autotest\] expand'
```

> `PanelPerfHooks`（六组实验开关）在正式实现后已移除，避免积累调试债；需要复测某因素时从本报告/git 历史恢复。

## 七、未采用 / 后续可选项

- **冻结毛玻璃**：实测对主线程无效，且有"动画瞬间变实/变暗"的视觉代价，不采用。
- **窗口背景改不透明**：可进一步压低 WindowServer/GPU 成本，但破坏菜单栏面板的通透质感，不采用。
- **`NSDisplayLink` 替换 Timer**：仅对 dev 版 60Hz Timer 有意义；feature 版已不用 Timer 驱动。
- **补全采样推迟**：`fans`/`bluetoothDevices` 等 `@Published` 未被 `expansionAnimationDeadline` 推迟，但实测落在 0.15s 窗口概率低、贡献小，暂不处理；若日后出现偶发卡顿可纳入。
