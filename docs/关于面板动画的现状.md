# 面板展开/收起动画：问题简报

> 本文件是**问题定义**，不是实施计划。任务定位：**根本性重构这套动画的实现架构**，性能问题与架构问题一起解决；具体解法不预设，由接手者自行设计。
> 面向任何 agent / 模型，零上下文可接手。工程约定（构建命令、设计纪律、注释规范）见仓库根 `AGENTS.md`。
> 历史四轮实装尝试已全部否决，列为 §4 的**禁止尝试清单**；过程细节存档于《面板动画尝试档案.md》（背景资料，无方向价值）。
> 基线：`dev` 分支当前 HEAD（本文撰写时为 `c46fc152`，其后动画链路若有变动以代码为准）。

---

## 1. 现象与问题

面板行展开/收起动画在部分工况下明显卡顿，且表现随设备差异极大：

| 工况 | 表现 |
|---|---|
| 60Hz 外接屏 | 「一顿一顿」，卡得无法与其他软件的同类动画相比 |
| 120Hz 内屏 | 掉帧被高刷新率掩盖，观感「还行」 |
| 120Hz 内屏 + 系统高负载 | 系统负载高时没有额外性能可分配，掉帧严重，观感「不行」 |
| 120Hz 内屏 + 省电模式 | 系统降频到 60Hz，问题复现且明显 |
| 自动化测试（大行程、快初速） | 表面「非常流畅」，掉帧被掩盖 |

用户判定：这不是弹簧参数没调好，也不是靠局部优化能修的瑕疵——**实现这套动画的架构本身就存在问题**，性能退化是该架构的产物。因此：

- 任务是**重新设计这套动画的实现架构**，从根本解决；在现有实现上做参数调整、局部优化或补丁式修补，不构成本任务的解；
- 新架构必须能说清：旧架构为什么在低刷新率、降频、系统高负载下必然退化，新架构为什么不会。

## 2. 验收标准（唯一验收依据，不可协商）

### 2.1 视觉只能等同或更好

弹簧动画的视觉与手感用户明确满意，以下各项**全部保持**：非线性弹簧节奏、内容自上而下卷出（内容静止、揭示边界下移）、下方行平滑推移、快速连点时中断保速度续接。曲线、时长、方向、中断行为不许变。

视觉上**不允许任何削弱**：弹簧手感、观感、材质效果都只能等同或更好。「以视觉换性能」的方案不在解空间内。

### 2.2 逐帧不变量（本问题的核心验收）

内容高度变化时，面板必须紧密跟随内容，**可检验表述**：

- 动画进行中的**每一帧**，面板底缘与内容最后一行可见边缘的间距都必须恒等于收尾间距（10pt）；任何一帧这个间距变大或变小都是错的。
- 同理，被 toggle 行的揭示边界与下方第一行顶缘的间距（6pt）在每一帧都必须恒定。
- 「两个运动最终到达同一位置」不算合格——它们在**每一帧**都必须重合。暂停任意一帧，画面必须像一张正确的静止截图。

### 2.3 帧率无关

同一套代码必须在 60 / 75 / 120 / 144Hz、省电降频、系统高负载下都流畅，无任何按刷新率分支的路径。针对特定帧率调参的补丁式优化会被拒收——用户原话大意：本就不该绑定帧数做优化，应该让逻辑通用。

### 2.4 架构验收

- 交付物是一套**新的实现架构**，不是旧路径上的局部优化；
- 必须能从设计上解释性能来源：旧架构为什么必然在低刷新率、降频、高负载下退化，新架构为什么不会（不依赖「这一帧恰好处理得快」的运气）；
- 逐帧不变量由什么机制保证（构造保证 or 调参近似），是架构说明的核心问题之一。

### 2.5 警告：不要优化错目标

本问题历史上多次翻车的直接原因：把「CPU 时间下降 X%」「慢帧数减少」当成了验收目标去优化，指标做出来了、用户目测不通过。**性能指标只是诊断工具，验收只看 §2.1～§2.4**（用户目测 + 逐帧校验 + 架构自洽）。

## 3. 硬约束

- `AGENTS.md` 全部纪律适用：面板内禁止持续性逐帧动画（CADisplayLink 仅允许存在于短暂弹簧窗口内）、MonitorPalette 令牌、双渠道编译开关、注释规范等；
- 双 scheme（`HagimiMonitor` / `HagimiMonitorDirect`）构建均须通过；
- 采样与 UI 的现有数据流模型不得破坏（`MonitorStore` 主线程发布，面板隐藏期刷新门控等既有机制不被绕过）。

## 4. 禁止尝试的方向（历史四轮，均已实装并否决）

以下方案族**禁止直接尝试，也禁止换名或换变体重试**。列表是排除性记录，不是解空间地图；若确有本质不同的变体（失败根因被新设计结构性排除，而非「这次调好一点」），先向用户说明差异点、征得同意后再实施。

1. **窗口层同参弹簧跟随**（第一版；其成果已在 dev 现状中，属基线的一部分而非候选方案）：修复了窗口/内容分段跳变，但卡顿未解决。
2. **displayLink `preferredFrameRateRange` 帧率请求**（第二版）：120Hz 有效、60Hz 无效（60Hz 本无 cap），已撤销。
3. **布局一次落终值 + 合成器纯变换（mask 滑入揭示 + 下方行 offset 补偿）**（第三版）：main 无改善；收起时面板与内容双运动可见错位，目测否决。
4. **单一时钟（窗口弹簧为唯一运动源、内容全部作为从动视图逐帧更新）**（第四版）：与 dev 原版 A/B 对比被判无意义，已清理。
5. **静树直驱（动画期冻结 SwiftUI 树 + 离屏捕获分片接管视觉，窗口弹簧单时钟仿射驱动）**（第五版，2026-09-03）：性能达标（单行 main 445→141-194ms、慢帧 25-30→2-6、逐帧 gap 构造恒定）但**视觉被整体否决**——用户目测判「纯垃圾」，分支已删除。离屏捕获的材质观感与实时渲染存在用户可感知的差异，此路线整体出局。

## 6. 已实测的数据点（2026-08，开发机 Mac mini M4 + macOS 26）

以下为当时实测，供复现与对照；如何解读、是否仍成立，由接手者自行重新验证：

- autotest 度量（main = 动画窗口主线程 CPU 时间）：基线全量展开约 521ms / 单行 toggle 约 415ms；慢帧 26–29 个/次。autotest 全量展开是「整面板每帧都在变」的最坏情况代理，用户单行点击场景约为其 78%。
- 诊断矩阵（env 开关逐项排除）：关全部内容动画 main 约 250ms（内容动画机制占约 290ms）；再停窗口弹簧约 208ms（窗口弹簧仅约 40ms）；行玻璃换静态填充无变化；mask 滑入动画与 frame 高度动画无差别。
- `sample` 抓动画期主线程热点：`RB::DisplayList::RenderState::RootTexture::render`（RenderBox 渲染侧符号），未见布局热点。
- **两个相互矛盾的数据点，未定论**：2026-08-28 曾把逐帧布局改为纯变换实测 main −43%（代码已删不可复现）；其后实装的「布局落终值 + mask」方案同场景 A/B 却无改善（约 521→约 540ms）。
- 窗口层加 `preferredFrameRateRange(60, 240, preferred: 120)` 实测：120Hz 屏弹簧帧间隔从 16-37ms 抖动变为稳定 8.3ms；60Hz 屏完全无效（本就不存在 cap）。
- 以上诊断性实验（如玻璃换静态填充）是测量手段的记录，不构成任何视觉削弱的授权（§2.1）。

## 7. 验证设施与方法

### 7.1 自动度量

- `HAGIMI_PANEL_AUTOTEST="<间隔秒>:<次数>"` 启动 app：自动定时 toggle 面板 + 主线程帧探针 + `AutotestPerfMeter` 度量；日志关键字 `[autotest]`（`expand ... main= proc= slowframes= wall=` 汇总行、`springStep gap` 帧率）。
- 口径：`driver.natural` 是展开区明细高度而非面板总高，`sizeDidChange h=` 才是总高。
- 同一构建在不同 derivedDataPath 构建（worktree 与主仓库产物同名互踩会 test runner hung）。

### 7.2 逐帧校验（改动前必做）

**agent 看不见动画**——用户的目测结论需要逐帧证据支撑，这是历史上反馈被误读的直接原因（「面板和内容不同步」被当成模糊形容词，而不是被逐帧定位）。改动前先搭建逐帧验证手段（如录屏抽帧、逐帧比对面板底缘与内容边缘间距），把 §2.2 不变量变成可检查的帧序列。

### 7.3 人工目测（最终验收）

四工况手动点击：60Hz 副屏、120Hz 主屏、省电模式、系统高负载；**每一轮改动必须与 dev 原版 A/B 对比目测**。观感优先于任何指标。

### 7.4 已知陷阱

- 不同路径的 ad-hoc Debug 产物会被系统重新索要蓝牙授权（弹窗挂起 app 且自动化不可见）——自动化验证优先用 App Store 版产物；手动测试前先在系统设置→隐私与安全性→蓝牙里给产物授权。
- autotest 自带 seq 每 1.2s 自动 toggle archive 分组；日志里 `applyWindowHeight anim=1` 连续出现是 seq 在跑，不是生产路径。
- Direct 版面板窗口的 CGWindowOwnerName 是 `HagimiMonitor`（Info.plist 名），窗口探测按此匹配。

## 8. 交付要求

1. 交付前必须回答：§2.2 逐帧不变量在新架构里**由什么机制保证**——构造保证还是调参近似；并实测首拍（toggle 第一帧）与中断重定向（动画中反向 toggle）两处。
2. 交付物附架构说明（对应 §2.4）：旧架构为何必然退化、新架构为何不会、不变量由什么保证。
3. 每轮产出可运行构建产物供用户与 dev 原版 A/B 目测；用户满意才算完成，指标达标不算。
4. 视觉只能等同或更好（§2.1）；任何涉及观感、材质、效果的改动先与用户对齐。
5. 实验方案走独立分支/worktree（独立 derivedDataPath 构建），不动 dev 工作区。
