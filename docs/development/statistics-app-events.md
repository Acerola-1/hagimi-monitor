# 应用高占用事件与时长口径

本文说明应用资源高占用事件的判定、时长与状态语义，以及 UI、报表和导出应遵循的
展示规则。实现以 `HagimiMonitor/Statistics/AppResourceEventStateMachine.swift`
与 `ProcessAlertCenter.swift` 为准；此处只记录难以从代码推断的口径决策。

## 为什么不再按采样次数计时

旧实现每收到一次高于门槛的读数就把时长加一分钟，于是两次相隔 60 秒的采样会显示
「已持续 2 分钟」，而且没有任何新输入 150 秒后就把事件写成「已恢复」。前者把观测
次数当时长，后者把「没看到」当成「已经好了」。两者都会让用户看到不可信的历史，
因此改为由有效覆盖区间累计。

## 三种时间必须分开

| 名称 | 含义 | 用途 |
|---|---|---|
| `continuousHighSeconds` | 本连续段内有效高占用覆盖的秒数 | 展示「高占用时长」、判定持续资格 |
| `eventSpanSeconds` | 首末观测之间的墙钟跨度 | 只作为背景，不能当作累计时长 |
| `observationCount` | 高占用观测次数 | 单独展示，不能折算成分钟 |

缺口会让跨度大于累计时长。展示时两者不得互相替代；设置页把次数标为「次高占用观测」，
时长标为「高占用 X」。

## 持续资格与最大间隔

- 持续资格默认 120 秒连续有效覆盖（`sustainedThresholdSeconds`）。未达资格的事件不进入
  展示列表，也不写入历史，避免把瞬时抖动记成一次事件。
- 首个瞬时样本不产生任何覆盖秒数：`t=0` 与 `t=60` 两次观测最多只证明 60 秒。
- 瞬时证据的最大间隔默认 90 秒（`defaultMaxGapSeconds`）。超过即视为连续性丢失。
- 来源给出真实覆盖区间时，直接采用区间长度，不再用观测间隔估算。

## 结束原因

| 原因 | 触发条件 | 是否算「恢复」 |
|---|---|---|
| `recovered` | 同一来源给出可靠的低于门槛观测 | 是 |
| `observationGap` | 未知观测超过最大间隔 | 否，记为中断 |
| `notObserved` | 应用未进入前列且无法复查 | 否 |
| `sourceFailure` | 采样来源失败 | 否 |
| `processExited` | 进程退出 | 否 |
| `suspended` | 睡眠、关闭记录或重启 | 否 |
| `replaced` | PID 复用或进程被替换 | 否 |

结束端点停在最后一次有效高覆盖处，不外推到未观测时段。唤醒、重新开启记录或重启后
建立新基线，不把暂停前后的高占用接成一段。

## 指标分批与多指标合并

采样按 CPU、GPU、内存、网络分批到达。某一批返回时只更新该批实际包含的维度：
空数组不是其他维度「已恢复」的证据。同一应用同时出现多项指标时，应用级时长是各区间
的并集（`unionSeconds`），重叠的那一分钟只算一次，不能相加。

## 门户与归属

- 门槛与档位边界来自 `StatisticsMetricDefinition`，事件中心不重复硬编码阈值。
- 内存门槛为 `max(3.5 GiB, 物理容量 × 20%)`，容量未知时退回绝对门槛。
- CPU 百分比以单逻辑核 100% 为基准，可超过 100%，80% 档位不称「整机满载」。
- 高占用不等于系统压力，通知与文案只描述同期事实，不写确定因果。

## 范围与加权口径

- 筛选/聚合的每个桶代表 `[t, t + 桶宽)`，右开。结束端点恰为某天零点时，该天整天
  不属于本区间；应用日行与系统指标共用这一边界（`StatisticsProcessStore.dayRange`）。
- 预设范围按本地自然日推进（含今天向前数），不用固定 86400 秒滚动窗口，跨夏令时由
  Calendar 处理。
- 均值一律按有效秒数加权：`Σ(值 × 有效秒数) / Σ(有效秒数)`。首个没有覆盖秒数的样本
  只记录峰值与次数，不参与均值，避免一个没有时长权重的读数拉偏结果。
- 事件的应用级时长用各指标区间的并集，重叠部分只算一次。
- 覆盖率的分母是「整机清醒时长」，只扣除系统明确报告的休眠；应用退出或采样失败形成的
  空档仍计入分母，因为那段时间用户确实在用机器。

## 验证

- `AppResourceEventStateMachineTests`：持续资格、首次样本、最大间隔、恢复依据、
  生命周期结束原因、显式区间优先、多指标并集与空区间。
- `ProcessAlertCenterDurationTests`：以告警中心为集成面，验证两拍不成两分钟、
  真实秒数、可靠低值恢复、未入榜不恢复、挂起中断、分批不误恢复。
- 时间由注入推进，测试不真实等待。

## 通知政策

是否发送由 `AppAlertNotificationPolicy` 决定，发送动作由 `AppAlertNotificationDispatcher`
执行，两者分开以便用替身验证而不真的打扰用户。

- 默认只有同时满足「达到持续资格」且「同期存在有效系统压力」才发通知。占用高但系统压力
  正常或未知时不发系统通知，只在界面展示。
- 同期压力来自 `ProcessAlertCenter` 订阅 `MonitorStore.$modules` 后提取的档位，与
  `PressureAlertCenter` 使用同一份证据，不各自再判一次。
- 同一事件内只有严重度明确升级才再次提示；档位相同不重复打扰。
- 发送失败按有界重试（默认最多 3 次）；只有真正送达才保留「已通知」标记，失败时不虚记成功。

## 持久化与重启

确认事件落库到 `StatsAppEvent`（与进程库同一个 SwiftData 容器，属于加表迁移，
旧库不需要重建）。

- 只有达到持续资格的确认事件入库，瞬时尖峰不写历史。
- 按稳定事件 ID 幂等写入，重复投递或更新同一事件不会产生重复行。
- 查询按 `[from, to)` 取交集：完全在范围外的事件不进列表，跨边界事件仍返回。
- 重启时把仍标记为 `ongoing` 的事件终结为中断，结束点取记录的最后有效时刻，
  不能用启动时刻，否则应用未运行的时间会被算成持续高占用。
- 报表把落库事件与内存告警按事件 ID 去重后合并，因此历史不再受内存窗口限制。
