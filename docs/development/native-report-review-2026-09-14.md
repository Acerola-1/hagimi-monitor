**结论：原生化方向可保留，当前实现尚不能验收。问题涉及数值单位、缺失数据语义、时间范围一致性、功能遗漏与绘制性能，不只是视觉打磨。先修正确性，再处理交互与版面。**

## 1. 用户要求与审阅边界

用户允许移植时优化、强化内容，但不接受内容变少、空卡片占位、信息重复、擅自改变指标含义或交互明显卡顿。用户希望：

- 首屏有实际信息，不把“健康”作为没有充分依据的总判断。
- 电源、GPU 等图标与外部面板保持语义一致；系统进程没有真实图标时使用合适的 SF Symbols。
- “本机信息查询”不重复堆放后续 CPU、内存、连接等模块已经承担的详情。
- 查明 macOS 新式液态玻璃分段切换控件的真实 API 和版本要求。
- 先获得详细 review，修复由 Gemini 实施。

审阅依据：

1. 当前 Swift 代码、未改动的 HTML/JS、字符串目录、迁移设计及任务清单。
2. 通过原生 UI 自动化查看正在运行的 `/private/tmp/hagimi-builds/dev/HagimiMonitorDirect.app`，实际检查概览、CPU、洞察与硬件分类。
3. 本机 `NSImage(systemSymbolName:)` 小型探针；字符串 key 静态扫描。
4. Apple 官方 API、macOS 27 release notes、WWDC 文档。

本机环境：macOS 27.0，build `26A428`；当前命令行 Xcode 26.6（17F113），选中 macOS SDK 26.5。运行产物与源码表现相符，但本次没有重新构建、核验产物源码哈希或运行完整测试；不将其当作新构建验收。没有采集 Instruments trace，因此卡顿的具体耗时归因仍待 profiling。UI 自动化调用耗时不等于帧时间。

严重度：P1 = 错误结果、错误硬件/状态结论或主要体验受损；P2 = 功能缺失、内容/一致性/交互问题；P3 = 局部呈现改善。以下区分已确认缺陷、代码风险、原有设计问题和产品建议。

## 2. 应先修复的正确性问题

### R01 · P1 · 网络和磁盘累计量被当作速率显示【代码确认】

位置：

- `HagimiMonitor/Views/Report/ReportNetworkView.swift:98`、`:106`
- `HagimiMonitor/Views/Report/ReportDiskView.swift:93`、`:102`
- `HagimiMonitor/Views/Report/ReportDetailsTableView.swift:142`
- 对照 `HagimiMonitor/Resources/ReportTemplate.html:2278` 的 `rateFromTotal`。

`netDown/netUp/diskRead/diskWrite` 是桶内累计字节量。新趋势图只除以 MB 单位，没有除以桶秒数；悬停和表格直接调用 `formatBytesRate`。这会将分钟累计量放大成 60 倍速率、小时量放大成 3600 倍，日量同理。峰值字段另有自己的速率含义，不能再除一次。

修复：数据模型明确区分 `totalBytes`、`averageBytesPerSecond`、`peakBytesPerSecond`；趋势、悬停、表格共用转换结果。为保持原口径，桶平均速率沿用旧版 `total / bucketSeconds`。若未来改为“有效采样时间内平均”，必须另立产品语义，不能混入迁移。每日汇总应显示累计量，不加 `/s`。

验收：一分钟累计 60 MiB，趋势/悬停显示 1 MiB/s；一小时累计 3600 MiB，同样显示 1 MiB/s。峰值保持输入值；累计卡片分别为 60 MiB 和 3600 MiB；缺失不显示为 0。

### R02 · P1 · 刷新后选中范围和实际内容错位【代码与实机确认】

位置：`NativeReportViewModel.swift:92`、`:162`、`:177`、`:189`。

`load()` 不重置 `selectedRange`，却固定用 `.today` 聚合。实机顶部高亮“近一年”，粒度却为分钟，图表只显示 9 月 14 日。由于 `selectRange` 对相同值提前返回，再点一次“近一年”还可能无法纠正。

此外，切范围时先发布选中值，再后台计算；旧数据仍在屏，`isAggregating` 未被主界面消费。载入中选择范围时 `snapshot` 可能为空，而初次载入仍用今日覆盖。旧加载、旧聚合互相完成时缺少统一版本标识。

修复：建立一次性提交的展示状态，包含 snapshot revision、request id、范围、起止时间、粒度和聚合结果。区分“请求中的范围”和“正在展示的范围”；旧结果可保留，但必须明确正在更新。每次完成时在 MainActor 内检查请求版本和窗口是否仍有效。刷新保留当前范围并重算；关窗/重开遵循明确的轻量状态恢复策略。

验收：今日→近一年→刷新；自选→刷新；载入中切范围；快速连点四个范围；载入中关窗再开。所有情况下高亮、日期、粒度、数值一致，旧请求不覆盖新请求。

### R03 · P1 · 缺少历史样本被解释成“台式机／无物理风扇”【代码确认】

位置：`ReportDataAggregator.swift:291`、`:330`；`ReportPowerView.swift:25`、`:79`；`ReportThermalView.swift:25`、`:70`。

电池 `isSupported` 由所选范围的电量或电池历史是否存在决定。选择没有记录的日期就可能将 MacBook 描述成“AC 交流供电／台式机形态”。风扇 `hasFans` 由平均/峰值是否大于 0 决定，取不到、历史无数据或风扇停转都被解释成“被动散热／无物理风扇”。在沙盒渠道尤其容易出现。

修复：硬件能力与范围数据可用性分开。使用可证实的硬件/IOPS 能力判断；必要时三态 `supported / unsupported / unknown`。有风扇但当前 0 RPM 仍是有风扇；历史为空不能推断物理形态或当前供电。禁止以更漂亮的占位文字编造结论。

验收：MacBook + 空历史；有风扇设备 + 全 0 RPM；沙盒读不到风扇；真实无风扇机型；台式机无电池。各状态显示事实或“不具备足够数据”，不互相混淆。

### R04 · P1 · 未知状态显示成低压力或运行良好【代码确认】

位置：`ReportOverviewView.swift:46`、`:74`、`:127`；`ReportThermalView.swift:53`；`ReportMemoryView.swift:170`；`ReportEventsView.swift:62`；`ReportInsightsView.swift` 的空态。

- 评分为 nil 时默认 `.low`，圆环用 `score ?? 100` 画满，虽然数字是“—”，视觉仍表示满分、低压力。
- nil 评分原因被固定写成“不足 30 分钟”；实际评分还检查有效交集覆盖率，可能记录很久仍不达门槛。
- 热状态缺失回退为 `0%`。
- Swap 全缺失与全部真实为 0 都落到“内存充足”；0 swap 本身也不足以证明内存充足。
- 事件为空被写成“系统稳定”，无法区分未记录/缺列/未检测到事件。
- 洞察空态声称未发现瓶颈，而该算法并没有完整瓶颈诊断能力。

修复：为未加载、无样本、观测不足、不支持、数据中断、真实正常建立明确状态。评分空态用中性视觉；评分层返回原因或复用已有原因表达；0 与 nil 分别显示。不夸大“系统健康”“瓶颈诊断”的覆盖范围。

验收：空库、仅旧格式数据、交集小于 30 分钟、交集低于覆盖率门槛、全部 0 swap、全部 nil swap。截图及文案逐例检查。

### R05 · P1 · 热状态的 0～3 档位被直接乘 100 当百分比【代码确认】

位置：`ReportThermalView.swift:53`、`:122`；数据来源 `StatisticsRecorder.swift:475`。

`cpuThermalAvg` 来源为系统热状态档位，范围为 0～3，并非 0～1 比例。直接乘 100 可能显示 200%、300%；与温度共用图表数轴又加重误读。温度缺失时整个热图为空，即使有公开 API 的热状态数据也不显示，损害沙盒渠道。

修复：以现有热状态标签、各档累计时长或明确解释的历史档位展示；不能擅自除以 3 后称百分比。温度与档位用独立图或明确独立轴。温度不可用时保留真实热状态。整机功耗、芯片功耗等名称也要回查原始数据源，不能仅因字段叫 power 就扩大成“整机”。

验收：分别输入 0、1、2、3 及档位混合历史；没有温度但有热状态时仍可查询热状态。

### R06 · P1 · 热力图更换了指标，而且将日数据误当成小时数据【代码确认】

位置：`ReportDataAggregator.swift:607` 附近 `buildHeatmap` 及 `aggregate`；旧版 `ReportTemplate.html:2024`。

旧版使用小时层数据，单桶忙碌度为 CPU/GPU/内存压力的最大值。新版使用当前趋势的 `filtered` 行且只取 CPU。选择一年时趋势来自日桶，日桶时间通常在午夜，结果会把整天均值放入 00:00 格；其他小时看起来没活动。这是数据含义错误，不是图形样式变化。

修复：小时热力图始终消费小时数据，保留原忙碌度算法；小时数据只保留近一段时间时，明确实际覆盖范围。不要伪造全年小时分布。如果改名为“CPU 活动分布”或改为日历热图，须明确记录产品变化并保持适用粒度。

验收：只有 GPU 高负载的小时、只有内存压力高的小时、日数据存在而小时数据缺失、近一年但小时仅覆盖近 60 天。没有小时证据时不能画出午夜尖峰。

### R07 · P1 · 曲线缺口处理缺失，CPU 均值与峰值未显式分系列【代码确认，实机有异常形状】

位置：`ReportCpuView.swift:145`；`ReportNetworkView.swift:104`；`ReportDiskView.swift:99`；其余 Chart 实现。

CPU 的均值和峰值 `LineMark` 没有独立 `series`，固定颜色也不等于稳定的系列身份；实机曲线出现密集竖向连接、峰值线视觉混杂。所有趋势直接对现有行生成标记，缺失行没有分段标识；仅跳过 nil 会连接缺口两端。网络/磁盘更将 nil 转成 0，制造不存在的低谷。

修复：在图表输入层建立稳定的 `seriesID + segmentID`。按数据粒度及采样连续性在缺口处断线；均值、峰值、不同指标分别成系列。悬停落在无数据区时提示无观测，不能无限距离吸附到另一段的数据。P/E 核必须核对其是各自利用率还是可相加贡献，不能机械堆叠独立百分比。

验收：10 个点中间删除 3 个桶；某指标 nil 而另一个有值；均值恒 20、峰值恒 80。应为独立水平曲线及明确断点，无竖线往返，无补零，无跨睡眠插值。

### R08 · P1 · 压力事件“恢复”的证据被扩大【代码确认】

位置：`ReportDataAggregator.swift` 的 `deriveAlertEvents`；旧版 `ReportTemplate.html:1691`。

新版 `observedEnds` 把通用 `coverS` 也算作压力观测。压力事件后只有普通 CPU 记录、没有有效内存/热状态观测时，也可能把事件标成 recovered。新测试用后续只有 coverS 的行验证“恢复”，反而固化这个问题。

修复：恢复依据必须是相关压力维度的有效观测，优先与已有 `StatisticsOverviewModel`/压力状态机口径对齐。分别核对两维观测，不能仅因后来有任何采样就宣告恢复。保留各档位累计组成；不要只留下最坏级别。

验收：内存告警后只有 CPU 观测→不得宣告恢复；之后明确正常内存观测→恢复；后续观测超时→中断；热状态和内存分别失联。纠正现有测试预期，并说明相对旧算法的必要收紧。

## 3. 性能与生命周期

### R09 · P1 · 每秒广泛失效与全量图表构造【结构确认，耗时贡献待采样】

位置：`NativeReportView.swift:6`、`:52`；`NativeReportViewModel.swift:71`、`:208`、`:223`；各模块 `@ObservedObject`；`ReportUIHelper.swift:23`、`:75`。

所有模块和根视图观察同一个 ObservableObject。每秒更新 `@Published liveReadings`，会通知这些观察者，即使历史模型没有变化。源码注释声称“只更新右栏”，当前观察边界并没有实现这个保证。切模块会重建对应图表，图表又直接使用全部 rows；没有实现设计承诺的受控图表点数。视图计算中还有数组扫描、线性最近点搜索、反复创建 DateFormatter。

这是一组解释卡顿的高可信候选，不应声称已经证明“每次切换几秒全部由其中一个点导致”。本次短程 UI 检查没有建立重复、定量的延迟分布。

实施顺序：

1. 在当前原生版先记录一组基线：范围、原始点数、每图 mark 数、主线程 CPU、点击至稳定首帧耗时。
2. 用 Instruments Time Profiler + SwiftUI 更新分析确认点击时主线程热点；加 signpost 分隔读取、聚合、图表准备、发布与显示。
3. 历史内容消费不可变模块模型；实时右栏使用独立且范围狭窄的观察源。范围选择状态也不要让所有图表无差别观察。
4. 在后台按宽度/时间跨度准备绘图序列；缓存 key 包含快照版本、范围、模块、粒度及点预算。采用保峰值、保断点的降采样，不能简单 every-N 丢峰。
5. 只创建当前模块所需的重型内容；不要用“把所有模块都放进 ZStack 隐藏”换取切换速度。
6. 复用格式化器或适当的 FormatStyle；图表悬停使用有边界的二分查找，避免每次指针移动扫描全量 rows。
7. 加载轻量骨架或进度时保持导航响应，不允许用几秒动画掩盖阻塞。

验收建议（目标，不是已测结果）：选中反馈在 100ms 内；常用范围的缓存模块切换至稳定内容 p95 尽量低于 250ms；冷计算超过 250ms 要有可见进度且窗口仍能操作；主线程没有持续数百毫秒的大块计算。固定机器/Release 配置/数据跑至少 20 次，报告中位数、p95、最慢值及 trace，不以一次主观“顺滑”结案。

### R10 · P2 · 取消与发布之间仍有竞态；隐藏窗口仍运行实时定时器【代码风险】

位置：`NativeReportViewModel.swift:164`、`:198`、`:208`、`:232`。

检查 `Task.isCancelled` 发生在进入 MainActor 之前，排队期间可能已刷新/关窗；MainActor 闭包只检查 self。每秒计时器没有窗口可见性门控，最小化后仍发全量实时字典。取消也没有贯穿较长聚合步骤。

修复：在最终提交位置检查 request id、closed 状态与取消；资源生命周期统一归窗口 session。最小化/隐藏停推或明确降频；恢复时即时更新。不要读取跨线程的告警可变数组而假定安全，审计 `ProcessAlertCenter` 的现有隔离机制后在正确隔离域取得值快照。

验收：聚合中关闭、立即重开、连续刷新、最小化 30 秒、后台计算完成后再关窗。对象释放和 timer 不重启应有证据，不只看静态引用被设 nil。

### R11 · P2 · 导出/打印把重型 HTML 生成搬回了主线程【代码确认】

位置：`ReportWindowPresenter.swift:65`、`:113`。

外层虽是 `Task.detached`，内部若把整个 `StandaloneHTMLReportExporter.write` 放进 `MainActor.run`，包括模板/库资源处理、JSON、图标编码及文件写入，仍会阻塞主界面。

修复：UI 面板和确需 AppKit 隔离的最小操作留在 MainActor，数据编码、拼装、文件写入在后台。不要为了消除并发诊断把全部工作包回 MainActor，也不要无依据加 unchecked Sendable。

验收：大快照导出时可切换模块、拖动窗口；trace 确认主线程没有承担完整 HTML 生成。

### R12 · P2 · 临时打印缺少失败收尾和完整会话边界【代码确认与运行待验】

位置：`ReportWindowPresenter.swift:142`、`:165`、`:265`。

导航代理只实现 didFinish；加载失败没有清理路径，静态 `printWebView` 可能残留。调用 modal print 后立即置 nil，不是明确的完成回调管理；重复打印共用同一静态槽位。打印数据生成失败仅日志，没有用户反馈。

修复：独立打印 session，覆盖加载失败、脚本失败、取消、打印完成、重复请求、父窗口关闭。确认 NSPrintOperation 的完成回调，资源在正确节点释放。保留“仅打印才创建 WebKit”的边界。导出/打印是否跟随当前范围要明确：原网页产物包含全量可筛选数据，不能把默认今日打印冒充当前近一年视图。

验收：正常打印、取消、导航故障、快速重复打印、父窗口关闭；均不留下报表持有的 WebView。无需要求系统 WebKit 辅助进程在某个毫秒内退出，但必须验证本应用引用已经释放。

## 4. 功能、文案和图标

### R13 · P2 · GPU/电源/系统进程图标不符合已有契约【代码及符号探针确认】

位置：`NativeReportViewModel.swift:42`；`MonitorModels.swift:116`；`ReportAppsView.swift:141`。

本机探针结果：`bolt.battery = false`，`powerplug/display/display.2/terminal/app.fill = true`。电源导航引用不存在的 `bolt.battery`，这就是目前空白图标的直接原因。外部 GPU 用 `display`，新导航另写 `display.2`。无应用图标统一回退 `app.fill`，没有沿用系统进程的 terminal / WindowServer display 语义。

修复：导航与标题复用 `MonitorKind` 的语义映射；电源用现有 `powerplug`。应用真实图标优先，WindowServer 回退 display，一般系统进程回退 terminal；分类规则共享，不在各页面复制。未知图标源不阻止一行展示。不为这次修复重建整套图标库。

### R14 · P2 · 本地化缺失、复用错误 key、模板变量直接上屏【静态与实机确认】

### R22 · P2 · 使用真正的系统分段导航，明确 macOS 26 与 27 的区别【官方资料确认】

用户描述的控件属于分段内容导航。需要区分：

- `Picker(...).pickerStyle(.segmented)`：已有标准分段选择器。
- **macOS 27 新增 `TabsPickerStyle`，使用 `.pickerStyle(.tabs)`**：专门表达标签式导航/内容选择，macOS 外观与普通值选择不同，VoiceOver 按 tabs 朗读。
- AppKit 对应 `NSSegmentedControl.role` 的 `tabs` 角色；不是自己画一排 Button 再贴玻璃背景。
- Liquid Glass 整体设计从 macOS 26 引入，但不能把所有玻璃交互、27 的 tabs API 都说成 26 可用。官方 API 描述确认了样式和语义；精确的长按拖动光学效果仍应在目标 OS/SDK 原生样例中目测，不能仅凭文档承诺完全相同的动画。

官方来源：

- [TabsPickerStyle](https://developer.apple.com/documentation/swiftui/tabspickerstyle)：原生样式和 `.tabs` 示例，元数据标注 macOS 27.0+。
- [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)：AppKit role 与 SwiftUI tabs 新增项。
- [Build a SwiftUI app with the new design — WWDC25](https://developer.apple.com/videos/play/wwdc2025/323/)：26 的整体设计背景。
- [Modernize your AppKit app — WWDC26](https://developer.apple.com/videos/play/wwdc2026/289/)：27 的玻璃交互与系统界面更新。

当前项目的运行系统为 27，但选中 SDK 为 26.5。**`if #available(macOS 27, *)` 不能让旧 SDK 识别未知 API。** 实施时核对本机可用 Xcode、工程/CI 工具链后选定支持 27 API 的 SDK，不能只改运行时 guard。不要擅自全局切换 xcode-select 或下载大型工具链；明确工具链选择，必要时项目级 DEVELOPER_DIR。最低 macOS 15 支持保留。

方案：

1. CPU/GPU/内存这类内容标签，在支持的 SDK + macOS 27 下用 `.tabs`，旧系统回退标准 `.segmented`。类别过多时保持可发现性，不能挤成不可读的十几段。
2. 时间范围本质是过滤值，默认用标准 segmented picker；如产品将其定义为几个固定时间视图并使用 tabs，须同步可访问性语义，不只为了动画。自选日期独立成日期按钮，显示实际区间。
3. 在最小原生样例确认外观、拖动、键盘方向键、VoiceOver、减少动态效果、明暗模式，再接入报表。
4. 不在每个 segment 上分别加 glassEffect，不用自定义 DragGesture/常驻动画去模拟系统液态镜片。

用户这次明确要求研究新式系统控件，计划可以在报表导航控件上采用它；这不等于授权把菜单栏面板及所有内容卡片重新改成 Liquid Glass。后续若实施，应在相关专题文档中记录这个局部边界。
